## 2. 文档目的

本文档用于建立 AI 智能电商微服务平台的统一语言（Ubiquitous Language），确保产品、设计、开发、测试、运维和项目文档在描述同一业务概念时使用一致的术语。

统一语言将应用于：

- 产品需求文档；
- 领域事件风暴；
- 限界上下文划分；
- 聚合与领域模型；
- Java 类名、方法名和枚举名；
- 数据库表名和字段名；
- API 路径、请求参数和响应字段；
- RocketMQ 事件名称；
- 前端页面、菜单和按钮文案；
- 测试用例；
- 日志与错误信息；
- 项目演示和简历描述。

本文档不是简单的中英文翻译表，而是对每个业务词汇的含义、归属、边界和使用规则进行约束。

## 3. 统一语言基本原则

### 3.1 同一概念只使用一个主要名称

例如：

- 统一使用“商品”，不在同一语境中交替使用“产品”“货品”“物品”；
- 统一使用“订单”，不混用“交易单”“购买单”；
- 统一使用“库存锁定”，不混用“冻结库存”“预扣库存”，除非文档明确说明其等价关系。

### 3.2 同一名称不能表达多个不同概念

例如“用户”在商城和后台中可能代表不同身份，因此应明确区分：

- 商城用户：`Member`
- 后台管理员：`AdminUser`

不得在领域模型中都命名为 `User`。

### 3.3 术语以业务含义为主

数据库字段、接口名称和代码结构应服从业务语言，而不是由技术实现反向定义业务。

例如：

- 业务概念是“库存锁定”，而不是“update stock table”；
- 业务概念是“订单已支付”，而不是“payment_flag = 1”。

### 3.4 跨上下文同名概念允许模型不同

例如“商品”在不同上下文中可以有不同模型：

- 商品上下文中的商品：完整商品聚合；
- 订单上下文中的商品：订单商品快照；
- 搜索上下文中的商品：商品搜索文档；
- AI 上下文中的商品：商品推荐数据。

这些模型不能直接共用同一个实体类。

### 3.5 事件统一使用过去式

领域事件和集成事件表示已经发生的事实，统一使用过去式命名：

- 商品已上架；
- 库存已锁定；
- 订单已创建；
- 支付已成功；
- 订单已取消。

英文事件统一使用过去式或完成式语义，例如：

- `ProductPublished`
- `InventoryReserved`
- `OrderCreated`
- `PaymentSucceeded`
- `OrderCancelled`

### 5.3 权限编码规范

统一采用：

```text
资源:动作
```

示例：

```text
product:list
product:create
product:update
product:publish
product:unpublish

order:list
order:detail
order:ship
order:cancel
order:refund

inventory:list
inventory:adjust

system:user:list
system:user:create
system:user:update
system:role:list
system:role:update
system:menu:list
system:menu:update
system:feature:update
system:config:update
```

规则：

- 使用小写字母；
- 单词之间使用连字符或不分隔，项目统一建议使用单个英文单词；
- 使用冒号分隔资源和动作；
- 一个权限编码只表达一个明确动作；
- 权限编码不得与路由路径直接绑定；
- 权限编码不得在不同模块重复表达不同含义。

### 7.3 SPU 与 SKU 使用规则

示例：

```text
SPU：某型号手机
SKU：黑色 + 256GB
SKU：白色 + 512GB
```

统一规则：

- SPU 不直接管理实际可用库存；
- SKU 是下单、定价和库存管理的最小单位；
- 购物车中保存的是 SKU，不是 SPU；
- 订单明细中同时保存 ProductId 和 SkuId；
- 搜索结果可以按 SPU 展示，但价格和库存来自 SKU；
- AI 推荐最终必须返回可定位到真实商品和 SKU 的标识。

### 7.4 禁用表达

- 不使用“产品”代替业务中的“商品”；
- 不使用“规格商品”代替 SKU；
- 不将商品状态和库存状态混为一谈；
- “已上架”不等于“一定有库存”；
- “有库存”不等于“商品一定可售”。

| 购物车项 | Cart Item | `CartItem` | 购物车中的一个 SKU 及购买数量 |

- 加入购物车不锁定库存；
- 购物车价格不是成交价格；
- 购物车金额不是订单最终金额；
- 购物车项失效后不自动删除，应明确提示用户；
- 相同 SKU 在同一购物车中只保留一条记录并累加数量。

### 9.3 订单状态流转统一表达

```text
待付款 → 待发货

待发货 → 已发货
待发货 → 退款中
已发货 → 已完成
已发货 → 退款中
退款中 → 已退款
退款中 → 原订单状态
```

业务方法统一表达：

```text
Order.pay(...)
Order.cancel(...)
Order.closeForTimeout(...)
Order.ship(...)
Order.confirmReceipt(...)
Order.requestRefund(...)
Order.completeRefund(...)
Order.rejectRefund(...)
```

禁止直接使用：

```text
order.setStatus(...)
```

绕过聚合业务规则修改状态。

### 9.4 禁用表达

- 不使用“订单关闭”和“订单取消”表达两个不同概念，第一版统一将超时关闭视为取消的一种原因；
- 不使用“已付款”作为最终订单主状态，支付结果作为订单进入待发货状态的原因；
- 不将“退款”与“取消订单”混为一谈；
- 不将购物车金额称为订单金额；
- 不从当前商品表重建历史订单明细。

### 10.3 数量关系

第一版推荐保持以下约束：

```text
totalQuantity = availableQuantity + reservedQuantity + soldQuantity
```

但如果后续将 `soldQuantity` 设计为累计统计而非当前库存组成，则应在库存设计文档中重新定义。

无论采用哪种实现，都必须满足：

```text
availableQuantity >= 0
reservedQuantity >= 0
totalQuantity >= 0
```

### 10.4 术语选择说明

本项目统一使用：

- 中文：库存锁定；
- 英文：`Reserve Inventory`；
- 状态字段：`reservedQuantity`。

不使用以下混合表达：

- 冻结库存；
- 预扣库存；
- 占用库存；
- 锁库。

在对外文档中可以说明这些词语在其他系统中可能表示相近概念，但本项目统一使用“库存锁定”。

- 禁止使用 `float` 或 `double` 计算金额；
- API 需要统一金额单位；
- 项目建议后端使用整数分，前端展示时格式化为元。

### 17.2 数量

| 中文术语 | 推荐代码命名 | 说明 |
|---|---|---|
| 购买数量 | `PurchaseQuantity` | 用户购买某 SKU 的数量 |
| 可用库存 | `availableQuantity` | 可被新订单锁定的库存 |
| 锁定库存 | `reservedQuantity` | 已被订单占用的库存 |
| 库存调整数量 | `adjustmentQuantity` | 一次库存调整的变化量 |

统一规则：

- 数量必须为整数；
- 购买数量必须大于零；
- 库存数量不得为负数；
- 数量上限由系统参数控制。

### 17.3 时间

| 中文术语 | 推荐代码命名 | 说明 |
|---|---|---|
| 创建时间 | `createdAt` | 记录创建时间 |
| 更新时间 | `updatedAt` | 最后更新时间 |
| 支付时间 | `paidAt` | 支付成功时间 |
| 发货时间 | `shippedAt` | 发货完成时间 |
| 完成时间 | `completedAt` | 订单完成时间 |
| 取消时间 | `cancelledAt` | 订单取消时间 |
| 订单超时时间 | `paymentDeadline` | 待付款订单最晚支付时间 |

统一规则：

- 数据库存储统一使用明确时区；
- API 对外统一使用 ISO 8601 格式；
- 不使用模糊字段名 `time`；
- 时间点使用 `At` 后缀；
- 时间长度使用 `Duration` 或明确单位后缀。

## 29. 待确认术语

以下内容将在后续领域分析中进一步确认：

1. 订单退款是否独立为退款聚合；
2. 支付是否在后续版本拆分为独立支付上下文；
3. 商品聚合是否直接持有 SKU，还是 SKU 作为独立聚合；
4. 分类和品牌是否各自独立为聚合；
5. 购物车是否采用领域聚合持久化，或采用 Redis 轻量模型；
6. 库存总量、可用量、锁定量和已售量的精确数学关系；
7. 功能配置与系统参数是否属于同一聚合；
8. 后台操作日志是否归属系统上下文或独立审计模块；
9. AI 对话记录是否由 AI 服务独立存储；
10. 向量数据库的具体实现选型；
11. 订单“超时关闭”在代码中是否统一命名为 `cancelForTimeout` 或 `closeForTimeout`；
12. 退款拒绝后订单恢复到原状态的具体策略。

以上术语在确认前可以用于讨论，但不得提前固定到跨服务契约中。

## 31. 当前统一语言结论

本项目当前确定的核心统一语言如下：

```text
商城用户统一称为 Member
后台用户统一称为 AdminUser
商品标准模型统一使用 Product / SPU
实际销售与库存单位统一使用 SKU
购物车保存 SKU，不保存 SPU
下单前阶段统一称为订单预览
下单后核心对象统一称为 Order
订单中的商品信息统一称为 OrderItem Snapshot
下单占用库存统一称为库存锁定
取消订单恢复库存统一称为库存释放
支付后正式处理库存统一称为确认扣减
后台导航统一称为菜单
操作能力统一称为权限
运行时启停能力统一称为功能配置
可调整业务数值统一称为系统参数
AI 推荐功能统一称为 AI 智能导购
规则问答统一称为 RAG 智能客服
订单自然语言查询统一称为 AI 订单助手
```

本文档作为后续领域事件风暴和限界上下文分析的语言基线。任何业务模型、接口、事件和数据库设计原则上都应遵循本文档定义。
