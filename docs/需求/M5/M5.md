可以。M5 建议保持 **3 个 SDD 级 Requirement**，不要把“搜索接口、索引、配置项”再拆成更多 Change：

```text
REQ-M5-001 Elasticsearch 商品搜索
REQ-M5-002 商品搜索索引同步
REQ-M5-003 系统功能与参数配置
```

M5 的核心是把 M2 已经建立的商品数据升级成**高性能搜索能力**，同时建立后续 AI、运营、功能灰度都会使用的系统配置能力。

下面这版可以直接复制。

```markdown
# M5 搜索与系统配置

## 阶段目标

在商品、库存和基础交易能力已经建立的基础上，完成：

- Elasticsearch 商品搜索；
- 商品搜索索引构建；
- 商品索引增量同步；
- 索引重建；
- 搜索异常降级基础；
- 系统功能开关；
- 系统参数管理；
- 配置缓存；
- 配置动态生效；

等平台增强能力。

M5 完成后，需要形成：

Product
↓
Search Index
↓
Elasticsearch
↓
商城搜索 / AI 商品检索

以及：

Admin
↓
System Config
↓
Cache
↓
Java Services / Frontend / AI
```

# 一、M5 核心边界

M5 主要涉及两个上下文：

```text
mall-search
=
商品搜索索引和查询能力
```

```text
mall-system
=
功能开关和系统参数
```

同时依赖：

```text
mall-product
=
商品权威数据
```

必须明确：

```text
Product DB
=
Source of Truth
```

```text
Elasticsearch
=
Search Projection
```

因此：

> Elasticsearch 不是商品主数据库。

任何商品：

- 名称；
- SKU；
- 价格；
- 上下架状态；

最终权威数据仍然属于 Product Context。

# REQ-M5-001 Elasticsearch 商品搜索

**阶段：** M5 搜索与系统配置
**类型：** 搜索能力需求
**优先级：** P1
**前置依赖：** REQ-M2-003
**主要服务：** mall-search
**主要前端：** mall-web
**基础设施：** Elasticsearch

---

## 一、需求目标

建立独立商品搜索能力，使商城用户可以通过关键词快速搜索真实上架商品。

完成后至少支持：

- 关键词搜索；
- 分页；
- 分类筛选；
- 品牌筛选；
- 价格区间；
- 基础排序；
- 搜索结果商品展示。

商城商品检索从普通数据库筛选升级为 Elasticsearch 搜索。

---

## 二、搜索数据来源

搜索索引必须来源于 Product Context。

正确关系：

```text
mall-product
↓
Search Projection
↓
Elasticsearch
↓
mall-search
```

禁止：

```text
mall-search
```

成为商品主数据维护方。

搜索服务不得拥有修改：

- Product；
- SKU；
- Brand；
- Category；

业务状态的能力。

---

## 三、搜索文档

Elasticsearch 商品文档至少可以包含：

```text
productId
productName
categoryId
categoryName
brandId
brandName
mainImage
keywords
status
minPrice
maxPrice
updatedAt
```

根据最终搜索需求可以加入：

- SKU 摘要；
- 属性；
- 搜索标签；
- 销量；
- 发布时间；

等字段。

具体 Mapping 在 Design 阶段确定。

---

## 四、关键词搜索

至少支持根据：

```text
商品名称
关键词
品牌
分类
```

等字段进行搜索。

例如：

```text
用户搜索：
机械键盘
```

返回真实商城商品。

搜索结果必须只包含：

```text
当前允许展示的商品
```

例如下架商品不得作为正常搜索结果出现。

---

## 五、筛选能力

至少支持：

```text
categoryId
brandId
priceRange
```

等基础筛选条件。

例如：

```text
关键词：手机
品牌：Apple
价格：5000 - 10000
```

能够组合查询。

---

## 六、排序

至少支持：

- 默认排序；
- 价格升序；
- 价格降序；
- 新品排序。

如果后续有：

- 销量；
- 综合热度；

可以再增强。

M5 不要求建设复杂推荐排序模型。

---

## 七、分页

搜索必须支持标准分页。

需要避免一次性查询大量商品。

分页模型应与项目统一 API 响应规范保持一致。

---

## 八、搜索结果

搜索返回的是：

```text
Search DTO
```

而不是：

```text
Product Aggregate
```

搜索结果应只包含商城结果页真正需要的数据。

例如：

```text
productId
name
image
price
brand
category
```

避免直接复制整个 Product Domain Model。

---

## 九、商品详情边界

搜索负责：

```text
找到商品
```

商品详情仍然由：

```text
mall-product
```

提供。

推荐流程：

```text
搜索
↓
mall-search
↓
返回 productId + Search Summary
↓
点击商品
↓
mall-product Product Detail
```

不要让 Elasticsearch 逐渐成为完整商品详情的第二数据库。

---

## 十、库存边界

搜索索引原则上不要维护强实时库存作为交易依据。

可以展示：

```text
有货 / 缺货等弱实时信息
```

但最终可售库存仍属于：

```text
mall-inventory
```

订单创建仍必须重新校验库存。

---

## 十一、mall-web 搜索体验

商城前端至少支持：

- 搜索框；
- 搜索结果页；
- 搜索关键词；
- 分类筛选；
- 品牌筛选；
- 价格筛选；
- 排序；
- 分页；
- 无结果状态；
- Loading；
- Error。

用户点击商品后进入已有商品详情页面。

---

## 十二、搜索异常

需要处理：

- Elasticsearch 不可用；
- 查询超时；
- 索引不存在；
- 搜索结果为空。

M5 至少建立明确异常响应。

是否采用：

```text
数据库降级搜索
```

由 Design 决定。

如果实现降级，需要保证：

> 降级路径不能产生与正式商品状态明显冲突的数据。

---

## 十三、验收标准

- Elasticsearch 可以正常运行；
- mall-search 可以连接 Elasticsearch；
- 可以根据商品名称搜索；
- 分类筛选正常；
- 品牌筛选正常；
- 价格筛选正常；
- 排序正常；
- 分页正常；
- 下架商品不会正常出现在结果中；
- 搜索结果不直接返回 Product Aggregate；
- 搜索服务不修改 Product 主数据；
- mall-web 搜索页面正常；
- 搜索核心测试通过。

---

## 十四、非本需求范围

本需求不负责：

- 索引同步机制；
- Product Event；
- 推荐系统；
- AI 智能导购；
- 用户行为画像；
- 搜索推荐模型。

索引同步由 `REQ-M5-002` 完成。

---

# REQ-M5-002 商品搜索索引同步

**阶段：** M5 搜索与系统配置
**类型：** 数据同步需求
**优先级：** P1
**前置依赖：** REQ-M2-003、REQ-M5-001
**主要服务：** mall-product、mall-search

---

## 一、需求目标

建立 Product 权威数据与 Elasticsearch Search Projection 之间的同步机制。

确保：

```text
商品新增
商品修改
商品上架
商品下架
SKU/价格变化
```

能够合理反映到搜索索引。

同时建立：

- 单商品同步；
- 批量同步；
- 全量重建；
- 失败记录；
- 重试基础；

等能力。

---

# 二、索引生命周期

至少需要支持：

```text
Create Index
Rebuild Index
Delete / Replace Index
```

索引 Mapping 和 Settings 必须通过代码或部署配置管理。

不能依赖开发人员手工进入 Elasticsearch Console 创建生产所需 Mapping。

---

# 三、首次全量索引

系统第一次启用 Elasticsearch 时，需要能够：

```text
Product DB
↓
读取所有合法上架商品
↓
构建 Search Document
↓
Bulk Index
↓
Elasticsearch
```

完成首次索引构建。

---

# 四、增量同步

商品发生变化后，需要同步搜索索引。

至少考虑：

```text
Product Created
Product Updated
Product Published
Product Unpublished
Price Changed
```

对应搜索数据更新。

---

# 五、上架同步

商品上架：

```text
Product Published
↓
建立 / 更新 Search Document
```

保证上架商品可以进入搜索结果。

---

# 六、下架同步

商品下架：

```text
Product Unpublished
↓
搜索索引删除或标记不可搜索
```

下架商品不得长期继续出现在正常商城搜索结果。

具体采用：

```text
Delete Document
```

还是：

```text
status = OFF_SALE
```

由 Design 决定。

---

# 七、价格变化

SKU 价格发生变化后，搜索索引中用于列表展示的：

```text
minPrice
maxPrice
```

等价格摘要需要同步更新。

但：

```text
搜索价格
≠
订单可信成交价
```

订单仍然必须从 Product 服务重新获取实时价格。

---

# 八、同步幂等

相同商品同步请求重复执行时，不应产生错误数据。

例如：

```text
Product 1001 Published Event
× 2
```

最终只能得到正确的一份最新 Search Document。

---

# 九、乱序更新

需要考虑：

```text
旧商品更新
```

晚于：

```text
新商品更新
```

到达 Search Service 的情况。

应通过：

- version；
- updatedAt；
- eventVersion；

等方式避免旧数据覆盖新数据。

具体方案由 Design 决定。

---

# 十、同步失败

例如：

```text
Product 已更新
↓
Elasticsearch 暂时不可用
↓
Search Sync Failed
```

不能简单：

```text
log error
↓
永久丢失
```

M5 至少需要形成：

```text
Sync Failure Record
+
Retry
```

基础。

---

# 十一、手工重建能力

后台或运维需要具备：

```text
Rebuild Product Search Index
```

能力。

用于：

- Elasticsearch 数据丢失；
- Mapping 升级；
- 索引数据不一致；
- 环境初始化。

全量重建必须：

- 可重复执行；
- 有执行状态；
- 能发现失败；
- 不依赖手工逐条商品处理。

---

# 十二、索引一致性检查

需要具备基础检查能力，例如：

```text
Product 上架数量
vs
Search Index 数量
```

或者按：

```text
productId
```

检查是否存在明显数据缺失。

M5 不要求建设完整数据治理平台，但必须具备基本排错方式。

---

# 十三、与 M7 的关系

M5 可以先使用：

```text
同步调用
应用事件
后台任务
```

等适合当前阶段的同步策略。

M7 再将：

```text
Product Published
Product Updated
Product Unpublished
```

等重要跨服务同步升级为：

```text
RocketMQ
+
Outbox
+
可靠消费
```

因此 M5 不需要为了索引同步提前完成整个 M7。

---

# 十四、验收标准

- 可以创建搜索索引；
- 可以全量构建商品索引；
- 上架商品可以同步进入索引；
- 商品更新可以同步；
- 商品价格变化可以更新搜索摘要；
- 下架商品可以从正常搜索中消失；
- 重复同步保持幂等；
- 旧数据不会明显覆盖新版本；
- Elasticsearch 不可用时同步失败可追踪；
- 失败同步具备基础重试能力；
- 可以执行全量索引重建；
- 索引重建后搜索结果正确；
- 搜索同步测试通过。

---

## 十五、非本需求范围

本需求不负责：

- RocketMQ 最终可靠同步；
- Outbox；
- Dead Letter；
- AI Embedding；
- Vector Search。

这些属于 M7 / M6。

---

# REQ-M5-003 系统功能与参数配置

**阶段：** M5 搜索与系统配置
**类型：** 平台配置需求
**优先级：** P1
**前置依赖：** REQ-M1-002、REQ-M1-003
**主要服务：** mall-system
**主要前端：** mall-admin
**基础设施：** MySQL、Redis

---

## 一、需求目标

建立平台统一功能开关和系统参数管理能力。

避免后续：

```text
是否开启 AI 导购
是否允许游客购物车
订单默认配置
搜索默认参数
```

等系统行为全部硬编码在代码中。

完成后应能够通过后台维护：

```text
Feature Config
+
System Parameter
```

并通过缓存和配置读取机制使相关服务使用。

---

# 二、配置分类

建议将系统配置分成两类。

## 1. Feature Config

控制：

```text
功能是否启用
```

例如：

```text
ai.shopping.enabled
ai.rag.enabled
mall.guest-cart.enabled
search.enabled
```

---

## 2. System Parameter

控制：

```text
功能运行参数
```

例如未来：

```text
cart.max-item-quantity
order.default-timeout-minutes
search.default-page-size
ai.max-tool-calls
```

具体参数在后续 Requirement 需要时逐步增加。

M5 不需要一次预定义整个项目所有参数。

---

# 三、配置模型

至少需要表达：

```text
configKey
configValue
configType
category
description
enabled
version
updatedAt
```

具体模型由 Design 决定。

要求：

```text
configKey
```

稳定且唯一。

---

# 四、配置类型

配置值应支持明确类型，例如：

```text
STRING
INTEGER
DECIMAL
BOOLEAN
JSON
```

读取配置时应按声明类型解析。

不要让所有配置最终都变成：

```text
String
```

然后业务代码到处自己解析。

---

# 五、配置默认值

业务代码使用配置时必须有明确策略：

```text
配置存在
→ 使用配置值

配置不存在
→ 使用安全默认值 / 明确失败
```

不能因为数据库暂时缺少一条非关键配置就导致整个服务无法启动。

具体：

```text
Required Config
Optional Config
```

由 Design 区分。

---

# 六、后台配置管理

mall-admin 至少提供：

- 功能开关列表；
- 开启/关闭功能；
- 系统参数列表；
- 修改参数；
- 参数分类；
- 参数说明。

必须接入 M1 RBAC。

例如可以规划：

```text
system:config:read
system:config:update
```

具体权限码由 Design 确定。

---

# 七、高风险配置限制

不是所有配置都允许后台任意修改。

尤其以下内容不能直接作为普通动态系统参数：

```text
Database Password
Redis Password
JWT Secret
LLM API Key
Cloud Secret
MinIO Secret Key
```

这些仍应由：

```text
Environment Variable
Secret Management
```

管理。

系统配置模块不能演变成：

```text
所有 Secret 的数据库仓库
```

---

# 八、Redis 配置缓存

为了避免每次业务请求都查询：

```text
mall-system DB
```

需要建立 Redis 配置缓存。

推荐：

```text
Business Service
↓
Config Client
↓
Redis
```

或者通过确定的内部配置服务机制实现。

具体跨服务读取模式由 Design 决定。

---

# 九、缓存失效

修改配置后：

```text
Database Update
↓
Cache Invalidate / Refresh
↓
后续读取使用新配置
```

必须避免：

```text
数据库已经修改
↓
Redis 永久还是旧值
```

---

# 十、动态生效

对于允许动态生效的配置，需要在合理时间内反映到业务系统。

例如：

```text
AI 导购开关：
ON
↓
后台改为 OFF
↓
AI 导购入口/服务按照设计关闭
```

但需要区分：

```text
Dynamic Config
```

与：

```text
Restart Required Config
```

不是所有底层技术参数都适合热修改。

---

# 十一、Feature Flag

Feature Flag 应支持：

```text
Enabled
Disabled
```

后续可扩展：

- 环境；
- 用户；
- 灰度比例；

但 M5 不需要建设复杂 Feature Flag SaaS。

首期重点解决：

> 平台功能能够无需修改代码完成启停。

---

# 十二、配置版本

重要配置变更应具备：

```text
version / updatedAt
```

等版本语义。

防止旧缓存或旧消息覆盖较新配置。

---

# 十三、配置审计

关键配置变更需要记录：

```text
谁
修改了什么
从什么值
改为什么值
什么时候修改
```

尤其：

```text
Feature Flag
```

和重要运行参数。

不得出现：

```text
配置突然变了
但完全不知道谁改的
```

---

# 十四、服务使用方式

业务服务不得：

```text
到处直接 SELECT system_config
```

也不得：

```text
每个服务实现一套 Config DAO
```

应该形成统一：

```text
Config Access
```

边界。

例如：

```text
SystemConfigClient
FeatureFlagService
```

具体设计由 SDD Design 确定。

---

# 十五、前端功能开关

部分 Feature Config 可能影响：

```text
mall-web
mall-admin
```

页面显示。

例如：

```text
AI 导购是否展示
```

可以通过后端公开安全配置 API 返回。

但：

```text
前端隐藏
```

不能成为真正的安全控制。

例如关闭某个敏感功能时：

```text
Frontend Hide
+
Backend Reject
```

都需要生效。

---

# 十六、验收标准

- 可以创建/维护 Feature Config；
- 可以创建/维护 System Parameter；
- configKey 唯一；
- 支持明确配置类型；
- 配置可以查询；
- 配置可以修改；
- mall-admin 页面可管理配置；
- 接口受 RBAC 控制；
- 配置能够缓存到 Redis；
- 修改后缓存能够正确失效；
- 动态配置能够按照设计生效；
- 功能关闭后相关后端行为正确；
- Secret 不进入普通系统参数；
- 配置变更能够审计；
- 配置相关测试通过。

---

## 十七、非本需求范围

本需求不负责：

- Nacos 全量配置中心迁移；
- Secret Manager；
- 复杂灰度发布；

# M5 Integration Gate

三个 Requirement 完成后执行阶段联调。

---

## 场景一：商品搜索

```text
后台存在上架商品
↓
商品进入 Elasticsearch
↓
mall-web 输入关键词
↓
mall-search 查询
↓
返回真实商品
↓
点击商品
↓
进入 Product Detail
```

必须成功。

---

## 场景二：商品修改

```text
商品名称 = iPhone 17
↓
同步索引
↓
搜索新名称
```

可以查到最新结果。

---

## 场景三：商品下架

```text
商品当前可搜索
↓
后台下架
↓
同步索引
↓
再次搜索
```

不得作为正常可售商品出现。

---

## 场景四：价格变化

```text
SKU Price
100
↓
修改为
120
↓
Search Sync
```

商品列表价格摘要应最终更新。

但订单仍然通过 Product API 获取可信实时价格。

---

## 场景五：Elasticsearch 故障

模拟：

```text
Elasticsearch Unavailable
```

系统：

- 不应产生不可理解的 500；
- 错误可定位；
- 同步失败可恢复；
- 如果设计了降级，则降级正确执行。

---

## 场景六：功能开关

例如：

```text
feature = ON
↓
业务功能正常
↓
后台改为 OFF
↓
Cache Refresh
↓
功能关闭
```

必须按照设计生效。

---

## 场景七：缓存一致性

```text
Config = 10
↓
业务服务读取 10
↓
后台改为 20
↓
缓存失效
↓
业务服务读取 20
```

不能长期读取旧值。

# M5 完成后的系统状态

最终形成：

```text
Product Context
      │
      │ Product Projection
      ↓
Search Context
├── Elasticsearch
├── Keyword Search
├── Filter
├── Sort
├── Pagination
└── Index Lifecycle
      │
      ↓
mall-web Search
```

同时：

```text
mall-admin
      ↓
mall-system
├── Feature Config
├── System Parameter
├── Config Audit
└── Redis Cache
      ↓
Java / Frontend / AI
```

M5 最终解决：

> **“商品怎么被快速找到，以及平台功能和运行参数怎样在不修改代码的情况下统一配置和动态控制。”**
