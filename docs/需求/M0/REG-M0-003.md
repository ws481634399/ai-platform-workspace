# REQ-M0-003 AI Service 基础工程

**阶段：** M0 项目初始化
**类型：** 工程基础需求
**优先级：** P0
**前置依赖：** 无强依赖，可与 `REQ-M0-001`、`REQ-M0-002`、`REQ-M0-004` 并行开发
**Repository：** AI Service 独立代码仓库
**远程地址：** https://github.com/ws481634399/ai-platform-AIService.git

---

## 一、需求目标

建立 AI 智能电商微服务平台独立的 Python AI Service 工程基线，为后续 AI 智能导购、商品对比、RAG 智能客服、订单助手和 Agent Workflow 等能力提供统一运行基础。

完成本需求后，AI Service 应具备：

- 独立 Python 工程；
- 独立依赖管理；
- 独立启动能力；
- FastAPI HTTP 服务；
- 配置管理；
- 日志能力；
- 健康检查；
- LLM Client 抽象；
- Java Backend API Client 抽象；
- AI Tool 扩展基础；
- 自动化测试基础；
- 环境变量与密钥管理；
- 可独立构建和运行的工程规范。

本需求只建立 AI 工程基础，不实现正式 AI 业务功能。

# 三、Python 版本管理

AI Service 项目统一使用：

```text
Python 3.11
```

即使开发机器系统默认 Python 为其他版本，也不得依赖系统默认版本运行项目。

使用 uv 管理项目 Python。

项目应明确固定 Python 版本，例如：

```text
.python-version
```

对应：

```text
3.11
```

要求开发环境能够通过 uv 创建和使用项目独立 Python 环境。

# 四、依赖管理

AI Service 统一使用：

```text
uv
+
pyproject.toml
+
uv.lock
```

进行依赖管理。

禁止同时维护多套互相竞争的依赖体系，例如：

```text
requirements.txt
Poetry
Pipenv
Conda
uv
```

混合管理同一个项目。

项目主要依赖声明写入：

```text
pyproject.toml
```

实际锁定版本形成：

```text
uv.lock
```

`uv.lock` 必须提交 Git。

`.venv/` 不提交 Git。

# 六、FastAPI 应用基础

建立独立 FastAPI Application。

至少提供：

- Application 创建入口；
- API Router；
- 配置加载；
- 应用启动；
- 基础异常处理；
- 健康检查接口。

例如：

```text
GET /health
```

健康接口至少能够说明：

```text
service
status
```

例如语义：

```json
{
  "service": "ai-service",
  "status": "UP"
}
```

具体响应规范在 Design 阶段确定。

M0 不需要创建 AI Chat 等正式业务接口。

# 八、日志基础

建立 AI Service 统一日志能力。

至少支持：

- 日志级别；
- 时间；
- Logger Name；
- 请求基础信息；
- 异常日志；
- TraceId 扩展能力。

```text

```

# 九、LLM Client 抽象

建立 LLM 调用的基础抽象。

目标不是现在接入所有模型，而是防止后续业务代码直接绑定某个 Provider SDK。

推荐依赖方向：

```text
Agent / Workflow
      ↓
LLM Client Interface
      ↓
Provider Adapter
      ↓
OpenAI / 其他 Provider
```

业务 Agent 不应到处直接：

```text
new ProviderClient(...)
```

或者读取：

```text
LLM_API_KEY
```

要求：

- LLM Provider 配置集中管理；
- LLM Client 有稳定调用边界；
- Provider 具体实现可替换；
- API Key 从环境配置获取。

M0 可以只提供接口和最小实现骨架。

---

# 十、Java Backend API Client

AI Service 不直接访问 Java 微服务数据库。

AI 需要获取：

- 商品；
- SKU；
- 订单；
- 用户；
- 库存；

等业务数据时，应通过 Java Backend 提供的 API 获取。

因此 M0 建立统一 Java API Client 基础。

推荐关系：

```text
AI Agent
   ↓
Tool
   ↓
Java API Client
   ↓
Gateway / Internal API
   ↓
Java Microservices
```

需要预留：

- Base URL；
- Timeout；
- Header；
- TraceId；
- 身份信息；
- 错误转换；
- 重试策略扩展。

M0 不需要实现正式：

```text
ProductClient
OrderClient
InventoryClient
```

完整业务能力。

# 十三、Prompt 管理基础

Prompt 不应大量直接硬编码在：

```python

```

等业务逻辑中。

应为后续 Prompt 提供独立管理位置。

- Prompt Template；
- Prompt Version；
- 参数化 Prompt。

---

# 十四、异常处理

建立 AI Service 基础异常体系。

至少能够区分：

- 参数错误；
- 配置错误；
- Java API 调用失败；
- 外部 AI Provider 调用失败；
- 系统内部异常。

API 不应直接向调用方暴露完整 Python StackTrace。

日志中可以记录必要异常信息用于定位，但不得泄露敏感数据。

# 十八、与 Java 后端的边界

必须明确：

```text
Java Backend
=
业务权威数据和业务规则
```

```text
AI Service
=
AI 推理、Agent、Workflow、RAG、Tool Orchestration
```

AI Service 不成为第二套业务系统。

禁止：

```text
AI Service
→ 直接连接 mall_order 数据库
```

禁止：

```text
AI Service
→ 直接修改商品/订单/库存表
```

正确方式：

```text
AI
↓
Tool
↓
Java API
↓
Java Domain
```

即使以后需要 AI 执行写操作，也必须通过 Java 业务 API 执行。

---

# 十九、写操作安全边界

M0 只建立设计原则。

后续涉及：

- 取消订单；
- 修改订单；
- 修改用户数据；

等 AI 写操作时：

必须经过：

```text
Agent
↓
Tool
↓
Java Backend API
```

不能由模型直接操作数据存储。

高风险写操作应为后续二次确认机制预留能力。
