## 1. 需求要点

- 做什么：在 mall-product 增加商品发布（上架/下架）与商城/内部两类读契约——商城列表、详情、内部 SKU 快照查询，并落地领域事件语义。
- 给谁：商城用户（mall-web）浏览真实可售商品；mall-cart/mall-order/ai-service 消费内部查询契约构建订单快照。
- 解决什么问题：把 REQ-M2-002 维护的草稿商品"激活"为可售商品，并解决"商品主数据随时间变化、历史订单不可漂移"的核心问题（快照）。
- 隐含需求：
  - 上架校验成为聚合内发布能力（ProductPublishability），程序化保证不满足条件不能上架；
  - 下架不影响历史快照；商城查询必须过滤下架/非 ON_SALE 商品；
  - 内部查询契约采用 DTO/Response 而非领域实体，防污染（防腐层/发布语言语义）；
  - 领域事件（Published/Unpublished/Changed）需要应用层可发布、注册到领域，但不强求 MQ 落地；
  - 商城列表基于数据库查询即可（M2 不引 ES），需要确定查询模型与索引（按分类/品牌筛选用二级索引）。
  - 上架成功可能依赖库存初始化联动（上架前校验"必要时至少一个 SKU 已完成库存初始化"，需与库存 Change 协商契约）。

知识检索结果（引用来源）：

- `product/06-聚合与领域模型设计.md` §7.1.9 商品上架不变量（名称/分类/品牌/至少一个启用 SKU/价格合法/规格不重复/未禁用/库存初始化）；§7.1.12 领域事件（ProductPublished/ProductUnpublished）；§7.1.10 publish() 示例。
- `product/05-上下文映射图.md` §10 商品→订单映射（订单防腐层、快照语义）；§11 商品→搜索映射（集成事件 ProductPublished 等，本阶段仅事件语义）；§14 订单→库存。
- `product/10-API与事件契约.md`：内部查询契约与事件 payload 规范，第一版事件建议只含必要标识。
- `product/07-核心业务流程.md`：商品上架→库存初始化→商城查询→详情→实时库存的端到端路径。
- `product/08-系统与微服务架构.md`：内部 API 走 Nacos 服务发现/OpenFeign 契约（mall-contracts），不允许跨服务直查数据库。

## 5. 待澄清问题

- 上架校验中"必要商品图片存在"与"库存初始化"两项的强制程度（必检 or 可配置）需 prd 裁量。
- 商城列表只返回可售商品时，"下架中"与"草稿"的过滤口径由商城 API 层处理还是查询模型过滤需 design 明确。
- 内部查询契约的批量能力（订单可能一次查多 SKU：Batch fetch by skuIds）需 design 与 M4 对齐。
- 商品快照契约的字段范围与存储归属（订单侧）需 prd 确认，M2 只定义契约。
- 领域事件的落点：本阶段是否提供 Outbox 表/仅领域事件注册，design 阶段确定（倾向仅领域事件 + 应用层可 handle，MQ 留 M7）。
- 缓存策略（列表/详情 Redis 缓存与失效时机）需 design 与 CHG-0011/0013 联动。
