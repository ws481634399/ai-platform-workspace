# Exploration（需求探索报告）

> 阶段：sdd-explore 产物
> 业界锚点：Discovery（Problem → Evidence → Conflict → Recommendation）
> 输入：requirement.md（原文沉淀；本文件不复述原文，只做分析）
> 产出状态：exploring（推进 Change 状态）

## 1. 需求要点

- 做什么：把 M2 已交付的后台商品/库存能力“翻面”到消费者侧——mall-web 首页、有效分类树/品牌公开接口、商品列表（分页筛选排序真实价区）、商品详情与规格选 SKU、库存三态聚合展示，并补齐游客公开访问与完整异常空态。
- 给谁：游客（核心用户，M3 浏览不强制登录）与 MEMBER；为 CHG-0018 加购提供 skuId/价格/库存展示底座。
- 解决什么问题：M2 的商城查询接口是半成品（价区为 null、经网关 401、分类品牌只有后台接口、库存没有面向商城的聚合），mall-web 目前只有 M0 骨架；本 Change 让商城第一次具备真实可逛的商品路径。
- 隐含需求：
  - 公开接口必须在网关显式匿名放行，同时 `/api/internal/**` 浏览器不可达（CHG-0015 已立规则，本 Change 新增的公开接口同步配置）；
  - 列表价区需要“启用 SKU 聚合”，排除无有效 SKU/下架商品，价格用整数分；
  - 库存查询必须批量化（详情一次拿全部 SKU 状态、列表页按需批量），杜绝 N+1；库存三态阈值（如 available=0 缺货，<N 库存不足）需 PRD 给定；
  - SKU 规格→唯一 SKU 的映射在服务端返回规格矩阵数据，前端做组合定位，禁用无货/不存在的规格组合；
  - 商品/SKU/分类/品牌所有 ID 以字符串到端（CHG-0015 统一序列化），前端 TS 类型一律 string；
  - 下架/失效商品的详情直接访问要有明确 404/不可售语义，不能静默展示；
  - 运营位（Banner/推荐/热门）首期可做最简选取（如按创建时间取新品），但结构要为后续运营留位。

知识检索结果（引用来源）：

- M3.md REQ-M3-002 全文与文末注意点 4/5（公开 API 清单、价区规则为用户明确决策）。
- `product/04` §BC-03 商品上下文（商品/SKU/分类/品牌权威，商城查询归其所有）、BC-06 库存上下文（只暴露可用库存语义）；`product/10-API与事件契约.md` 公开接口 vs 内部契约分层、禁止浏览器访问 internal。
- CHG-0012 已交付商城列表/详情与内部查询契约骨架（STORY-002-03-02-01、STORY-002-03-03-01），本 Change 在其上补全而非重做；CHG-0013 交付库存单/批查询，本 Change 消费批量能力并可能需要新增“面向商城的批量可售状态”适配。
- CHG-0015 为硬前置：网关放行、ID 字符串、价区修复未完成则本 Change 无法联调。

## 2. Story 归属判定

- Feature ID: FEAT-003-02（商城前台 → 商品浏览）
- Story 节点（本次新建 5 个）：
  - STORY-003-02-01-01 商城首页（FEAT-003-02-01 首页与公开分类品牌）
  - STORY-003-02-01-02 公开分类与品牌查询（FEAT-003-02-01）
  - STORY-003-02-02-01 商城商品列表（FEAT-003-02-02 商品列表与详情）
  - STORY-003-02-02-02 商品详情与 SKU 选择（FEAT-003-02-02）
  - STORY-003-02-03-01 SKU 可售状态聚合（FEAT-003-02-03 库存状态展示）
- 是否新建 candidate: 否（新建正式节点，FEAT-003 归属已确认）。
- Feature 路径: 商城前台 → 商品浏览 → 首页与公开分类品牌/商品列表与详情/库存状态展示 → 对应 Story。

## 3. 证据评估

- 业务依据：M3.md REQ-M3-002 验收标准 15 条 + Integration Gate 场景一（游客浏览全链路必须成功）；注意点 4/5 直接规定接口与价格规则。
- 工程依据：M2 商品/库存真实数据已在库（实测 33 条库存、商品 ID 2099488396675276801）；CHG-0012/0013 交付了可复用查询契约；mall-web M0 已交付 Vite/Vue3/TS/Router/Pinia/Axios 骨架。
- 结论: 充分。缺口在“面向商城的接口装配”而非领域未知。

## 4. 冲突点检测

- 与 specs 冲突: 无。
- 与既有 Change 重叠或沿用:
  - 价区 min/max 与“无有效 SKU 不展示”的**修复**在 CHG-0015（既有列表接口），本 Change **消费修复结果并扩展**（排序参数、前端页面、详情聚合）；边界以“改既有缺陷归 0015，加接口/页面归 0017”划分。
  - 库存批量可售状态：CHG-0013 已有内部批量查询则复用；若其语义（返回精确数字）不适合商城，本 Change 在 mall-product 侧做商城适配聚合（product→inventory Java API），不新增浏览器→inventory 直连。
  - 与 CHG-0018 契约耦合：购物车实时校验也需要同样的批量商品/库存查询能力，design 时接口形状需同时考虑两个消费者，优先放在 mall-product 的商城/内部适配层复用。
- 与已规划 Story 重复: 无（STORY-002-03-02-01 是“后台→商城查询接口骨架”，本批 Story 是“消费者侧完整体验 + 公开 API 补全”，层次不同）。
- 处理决策: 5 个 Story 按“入口（首页+公开基础数据）→ 列表 → 详情/SKU → 库存聚合”拆分；库存聚合单列 Story 因其跨 product/inventory 两服务且购物车复用。

## 5. 待澄清问题

- 库存三态阈值（库存不足门槛 N，建议 N=10 或取后台配置）由 PRD 定稿；M3 是否提供后台配置项建议不做，先用常量。
- 列表排序枚举（默认/价格升降/新品）具体集合与“新品/推荐/热门”首期选取规则（createdAt desc / 销量暂无则留空）由 PRD 明确。
- 品牌接口形态（全量有效品牌下拉 vs 分页）与分类树层级深度（M2 限制几级）需 design 核对 M2 数据模型。
- 详情库存聚合由谁调用 inventory：建议 mall-product 聚合后一次返回（前端只认 product），需 design 确认与 CHG-0013 内部契约的兼容及服务间凭证（CHG-0015）联动。
- 图片 URL 与 MinIO 访问基址、占位图策略在 design 结合 M2 图片字段现状确定。
- 游客接口限流/防刷是否 M3 引入：建议不做（网关层留 TODO），PRD 标注。
