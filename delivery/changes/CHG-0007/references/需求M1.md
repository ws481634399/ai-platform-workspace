# REQ-M1-001 统一身份认证体系

**阶段：** M1 身份与权限  
**类型：** 安全基础需求  
**优先级：** P0  
**前置依赖：** REQ-M0-001、REQ-M0-004  
**主要服务：** mall-identity、mall-gateway  
**主要前端：** mall-admin

## 一、需求目标

建立平台统一身份认证技术基线，支持 ADMIN、MEMBER、SERVICE 等不同主体类型，并在 M1 优先完成后台管理员认证闭环。

认证体系负责：

- 身份校验；
- 登录；
- Access Token；
- Refresh Token；
- Token 生命周期；
- 登录状态；
- 身份上下文；
- 服务间可信身份传播。

完成后，后续 M3 商城会员认证可以复用同一套身份基础，不需要重新设计一套 Token 与 SecurityContext 体系。

---

## 二、主要需求

### 1. 管理员账号认证

支持后台管理员：

- 用户名/账号登录；
- 密码校验；
- 退出登录；
- Token 刷新；
- 登录状态校验。

管理员密码必须安全存储，不得：

- 明文存储；
- 明文日志输出；
- 通过 API 返回密码或密码摘要。

---

### 2. Token 体系

采用：

Access Token

- Refresh Token

的双 Token 模型。

需要支持：

- Access Token 签发；
- Access Token 过期；
- Refresh Token 刷新；
- Refresh Token 过期；
- 主动退出；
- Token 撤销；
- 用户状态变化后的认证处理。

不得只实现“生成一个永久 JWT”。

---

### 3. 主体类型隔离

统一建立身份主体概念，至少能够区分：

- GUEST；
- MEMBER；
- ADMIN；
- SERVICE。

必须防止：

# 管理员 Token

# 商城用户 Token

服务 Token

这种主体混用。

认证成功后需要建立统一可信身份上下文，例如能够表达：

- subjectId；
- subjectType；
- username；
- traceId；
- 必要身份信息。

---

### 4. Gateway 与业务服务认证边界

Gateway 负责：

- 请求统一接入；
- Token 初步验证；
- 身份信息提取；
- 非法请求拦截；
- 可信身份向下游传播。

但 Gateway 不是最终权限中心。

必须保持：

Gateway
→ Authentication

Business Service
→ Authorization + Resource Ownership

例如：

“这个 Token 是否有效”

可以在 Gateway 判断。

但：

“这个管理员能不能删除商品”

必须由业务服务再次授权。

---

### 5. Spring Security 基础

建立统一 Spring Security 安全基础，使 Java 微服务能够获得当前可信身份，并为后续：

- RBAC；
- @PreAuthorize；
- API 权限；
- 资源归属校验；

提供基础。

---

### 6. 前端登录基础

mall-admin 完成基本登录流程：

登录页面
→ 提交管理员凭证
→ 获取 Token
→ 保存登录状态
→ 请求后台接口
→ 刷新 Token
→ 退出

完整动态菜单和按钮权限由 `REQ-M1-003` 完成。

---

## 三、验收标准

- 管理员可以使用正确账号密码登录；
- 错误密码不能登录；
- 禁用管理员不能正常建立有效登录态；
- 登录成功能够获得 Access Token 和 Refresh Token；
- Access Token 能被后端正确识别；
- Access Token 失效后可以按照设计刷新；
- Refresh Token 失效后必须重新登录；
- 主动退出后登录凭证按设计失效；
- ADMIN / MEMBER / SERVICE 身份能够区分；
- Gateway 能进行统一认证；
- 下游服务可以获得可信身份上下文；
- 密码、Token、Secret 不出现在普通响应和日志中；
- 基础认证自动化测试通过。

- 会员资料；
- 收货地址。

商城会员完整能力由 M3 实现。

# REQ-M1-002 后台 RBAC 权限体系

**阶段：** M1 身份与权限  
**类型：** 核心安全需求  
**优先级：** P0  
**前置依赖：** REQ-M1-001  
**主要服务：** mall-identity  
**依赖基础设施：** MySQL、Redis

## 一、需求目标

建立后台完整 RBAC 权限模型，使不同管理员根据角色拥有不同菜单、按钮和 API 权限。

核心授权模型：

AdminUser
↓
Role
↓
Permission / Menu
↓
API / Operation

最终权限判断必须发生在后端。

完成本需求后，后续：

- 商品管理；
- 库存管理；
- 订单管理；
- 系统配置；
- AI 知识库管理；

均可以直接使用统一权限体系，而不需要每个模块重新设计权限。

---

## 二、主要需求

### 1. 管理员管理

建立 AdminUser 管理能力。

至少支持：

- 管理员查询；
- 创建；
- 修改；
- 启用；
- 禁用；
- 角色分配。

管理员状态发生变化后，应能够影响后续认证和授权。

---

### 2. 角色管理

建立 Role。

至少支持：

- 创建角色；
- 修改角色；
- 查询角色；
- 启用/禁用；
- 给管理员分配角色；
- 给角色分配权限。

例如后续可以形成：

SUPER_ADMIN
PRODUCT_ADMIN
ORDER_ADMIN
OPERATOR

但具体角色初始化策略在 Design 中决定。

---

### 3. 菜单与权限模型

建立后台菜单和权限模型。

需要支持：

- 目录；
- 页面菜单；
- 按钮/操作权限；
- 权限编码；
- 菜单树；
- 排序；
- 启用/禁用。

例如未来权限编码可以表达：

product:read
product:create
product:update
product:publish
order:read
order:ship

具体编码规则在 Design 阶段统一。

---

### 4. API 权限控制

后端必须进行真实权限校验。

可以基于：

Spring Security

- @PreAuthorize

或设计阶段确定的等价机制。

要求：

无权限管理员即使绕过前端直接调用 API，也必须返回拒绝结果。

禁止：

“按钮隐藏了，所以接口不用验证权限”。

---

### 5. 权限缓存

权限数据可以使用 Redis 缓存，提高每次请求授权效率。

但必须同时设计权限失效机制。

例如：

管理员角色发生变化
↓
Permission Cache Invalidated
↓
下一次请求重新加载

同样适用于：

- 角色权限变化；
- 菜单权限变化；
- 管理员禁用。

不能出现管理员已经被移除权限，但缓存长期仍允许访问。

---

### 6. 权限管理审计

关键权限操作需要能够被审计。

至少关注：

- 管理员创建/修改；
- 管理员启用/禁用；
- 角色分配；
- 角色权限变更；
- 菜单权限变更。

具体完整操作日志体系可在后续系统管理需求继续增强，但 M1 必须保留安全审计基础。

---

## 三、核心安全规则

必须满足：

认证
≠
授权

例如：

用户已经登录
≠
用户可以操作所有后台 API

以及：

Role
≠
直接硬编码 Java if/else

权限应通过统一权限模型判断。

同时：

前端权限
≠
后端权限

后端才是真正安全边界。

---

## 四、验收标准

- 可以维护管理员；
- 可以维护角色；
- 可以维护菜单/权限；
- 可以为管理员分配角色；
- 可以为角色分配菜单/按钮/API 权限；
- 不同角色能够获得不同权限集合；
- 有权限 API 可以访问；
- 无权限 API 后端真实拒绝；
- 直接绕过前端请求 API 仍然受到权限限制；
- Redis 权限缓存正常；
- 权限修改后缓存能够正确失效；
- 禁用管理员后权限按设计失效；
- 不存在默认“登录即拥有所有权限”的情况；
- 关键权限操作具备审计基础；
- RBAC 核心测试通过。

---

- 商城会员权限。

# REQ-M1-003 后台动态菜单与权限前端

**阶段：** M1 身份与权限  
**类型：** 前端权限需求  
**优先级：** P0  
**前置依赖：** REQ-M1-001、REQ-M1-002 的菜单/权限契约  
**主要仓库：** ai-platform-frontend-web  
**主要应用：** mall-admin

## 一、需求目标

在 mall-admin 中建立完整的后台权限前端框架，根据当前管理员真实权限动态生成：

- 菜单；
- 路由；
- 页面访问能力；
- 按钮/操作入口。

不同角色登录后台以后，应获得与权限匹配的管理界面。

完成本需求以后，后续商品、库存、订单等后台模块只需要：

页面

- Route Metadata
- Permission Code

即可接入统一权限体系。

---

## 二、主要需求

### 1. 登录状态管理

登录成功后，mall-admin 应建立统一管理员登录状态。

至少管理：

- 当前管理员信息；
- Access Token；
- 登录状态；
- 当前菜单；
- 当前权限编码。

刷新浏览器后能够按照设计恢复合法登录状态。

---

### 2. 加载当前管理员权限

登录成功后，通过后端接口获取：

- 当前管理员；
- 菜单树；
- 权限编码集合。

前端不得自己根据角色名称硬编码全部权限。

错误：

if role == "admin":
showEverything()

正确：

Backend Permission
↓
Frontend Permission State
↓
UI

---

### 3. 动态菜单

后台侧边栏根据后端返回的菜单数据动态生成。

不同角色应看到不同菜单。

例如：

商品管理员
→ 商品相关菜单

订单管理员
→ 订单相关菜单

不应让所有管理员看到相同静态菜单。

---

### 4. 动态路由

将后端菜单权限映射到 mall-admin 中预定义的页面组件和路由。

需要支持：

- 动态注册路由；
- 页面刷新后的路由恢复；
- 未授权页面拦截；
- 404；
- 403。

必须特别注意安全：

> 服务端不能直接返回任意字符串，然后让前端动态执行任意组件路径。

应采用：

Backend Menu Code
↓
Frontend Component Registry
↓
Known Component

即只能映射前端已经明确注册的安全组件。

---

### 5. 按钮级权限

建立统一按钮/操作权限能力。

可以采用：

- Directive；
- Component；
- Composable；

等方式，Design 阶段确定。

例如：

有：

product:create

显示：

新增商品

没有：

product:create

则不显示或禁用对应操作入口。

后续业务页面不能每个页面重新自己实现一套权限判断逻辑。

---

### 6. 401 / 403 统一处理

统一处理：

# 401

未认证 / 登录状态失效

# 403

已经认证但没有权限

需要形成一致用户体验。

例如：

Access Token 失效
→ 尝试合法刷新或重新登录

无权限
→ 显示 403 或权限提示

不能把 401 和 403 全部当成“登录过期”。

---

### 7. Token 生命周期前端协作

与 `REQ-M1-001` 的 Token 体系协作。

需要处理：

- 请求携带 Token；
- Access Token 失效；
- Refresh；
- Refresh 失败；
- 退出；
- 登录状态清理。

应避免多个并发请求在 Token 失效时无控制重复刷新。

具体并发刷新策略在 Design 阶段确定。

---

### 8. 权限状态刷新

管理员权限发生变化后，需要能够在合理时间内反映到前端。

例如：

管理员失去商品发布权限
↓
重新获取权限
↓
发布按钮消失
↓
API 同时由后端拒绝

前后端权限必须最终一致。

---

## 三、核心原则

权限前端只负责：

可见性

- 导航
- 用户体验

不负责提供真正安全保障。

必须始终保持：

Frontend Permission
↓
UX Protection

Backend Permission
↓
Security Protection

即使用户通过浏览器 DevTools 手工修改 Pinia 权限状态：

后端 API 依然必须拒绝非法请求。

- 管理员登录后可以正常进入后台；
- 当前管理员信息能够正确加载；
- 菜单树能够从后端加载；
- 不同角色显示不同菜单；
- 动态路由能够正确生成；
- 浏览器刷新后动态路由能够恢复；
- 无权限页面不能正常进入；
- 按钮权限可以统一控制；
- 不同角色看到不同操作按钮；
- 401 能统一处理；
- 403 能统一处理；
- Token 失效处理正常；
- 退出后权限和登录状态被清理；
- 服务端菜单不能任意加载未知前端组件；
- 即使绕过前端权限，后端仍能拒绝非法 API 调用；
- mall-admin build / lint / type-check 通过。

基础框架。
