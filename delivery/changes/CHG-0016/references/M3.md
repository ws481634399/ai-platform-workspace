可以。M3 建议保持 **3 个 SDD 级 Requirement**，分别解决：

```text
REQ-M3-001 商城会员与地址
REQ-M3-002 商城商品浏览体验
REQ-M3-003 购物车
```

这一阶段开始真正把 **M1 的身份体系 + M2 的商品库存体系 + mall-web** 串起来，形成用户侧商城基础能力。

下面可以直接复制。

# 一、M3 核心边界

M3 涉及三个主要业务上下文：

```text
mall-identity
=
会员登录身份、密码、Token、认证状态

mall-member
=
会员资料、收货地址等会员业务数据

mall-cart
=
购物车及购物车业务规则
```

同时依赖：

```text
mall-product
=
商品与 SKU 权威数据

mall-inventory
=
实时库存权威数据
```

必须保持：

```text
Identity
≠
Member Profile

Product
≠
Inventory

Cart
≠
Order
```

M3 不允许为了方便将这些领域重新合并。

# REQ-M3-001 商城会员与地址

**阶段：** M3 商城基础  
**类型：** 商城会员需求  
**优先级：** P0  
**前置依赖：** REQ-M1-001  
**主要服务：** mall-identity、mall-member  
**主要前端：** mall-web

---

## 一、需求目标

在 M1 已建立的统一身份认证基础上，正式实现商城 MEMBER 主体的注册、登录和会员业务能力。

完成后普通消费者可以：

- 注册商城账户；
- 登录商城；
- 刷新登录状态；
- 退出登录；
- 查看和修改个人资料；
- 管理收货地址；
- 设置默认地址。

M1 已经建立：

```text
Access Token
Refresh Token
SubjectType
Gateway Authentication
SecurityContext
```

M3 不重新设计另一套认证体系。

商城会员直接复用统一认证基础，并使用：

```text
subjectType = MEMBER
```

---

## 二、会员注册

商城 `mall-web` 提供公开会员注册能力。

注册至少需要形成：

```text
注册凭据
↓
创建 Member Identity
↓
生成 memberId
↓
初始化 Member Profile
```

具体采用：

- 用户名；
- 手机号；
- 邮箱；
- 密码；
- 验证码；

中的哪种组合作为首期注册方式，由 Design 阶段确定。

但必须保证：

- 登录标识唯一；
- 密码安全存储；
- 不保存明文密码；
- 不在日志中输出密码；
- 注册失败不能产生不完整会员数据。

---

## 三、Identity 与 Member 边界

必须明确：

### mall-identity 管理

```text
memberId
登录账号
passwordHash
认证状态
Refresh Token
账户锁定
登录安全信息
```

### mall-member 管理

```text
memberId
nickname
avatar
profile
address
其他商城会员资料
```

例如：

```text
密码修改
```

属于：

```text
mall-identity
```

而：

```text
昵称修改
```

属于：

```text
mall-member
```

禁止在 `mall-member` 再保存一套登录密码。

---

## 四、会员登录

商城用户通过 mall-web 登录。

流程：

```text
mall-web
↓
Gateway
↓
mall-identity
↓
验证 MEMBER 身份
↓
Access Token + Refresh Token
```

Token 必须明确：

```text
subjectType = MEMBER
```

MEMBER Token 不允许作为 ADMIN 身份访问后台。

---

## 五、登录状态

mall-web 建立统一会员登录状态。

至少管理：

- memberId；
- 登录状态；
- Access Token；
- 必要会员信息。

支持：

- 页面刷新后的登录恢复；
- Access Token 过期处理；
- Refresh Token；
- 退出登录；
- 401 统一处理。

不得每个页面单独实现 Token 逻辑。

---

## 六、会员资料

建立 Member Profile。

至少支持：

- 查看个人资料；
- 修改昵称；
- 修改头像；
- 必要基础信息维护。

头像可使用 MinIO 对象存储。

M3 不需要建立复杂会员等级、积分、成长值等营销体系。

---

## 七、收货地址

建立 Address。

至少支持：

- 地址列表；
- 新增地址；
- 修改地址；
- 删除地址；
- 设置默认地址；
- 查询默认地址。

地址至少需要表达：

```text
receiverName
receiverPhone
province
city
district
detailAddress
postalCode（如需要）
isDefault
```

具体字段由 Design 最终确定。

---

## 八、地址核心规则

必须保证：

### 1. 地址归属

会员只能访问自己的地址。

例如：

```text
Member A
```

不得通过修改：

```text
addressId
```

读取或修改：

```text
Member B
```

的地址。

不能只依赖前端不显示。

后端必须校验：

```text
Address.memberId == CurrentMember.memberId
```

---

### 2. 默认地址

同一会员原则上只有一个默认地址。

当设置新的默认地址时，需要正确处理原默认地址。

---

### 3. 删除规则

删除默认地址后的处理策略需要明确。

例如：

- 无默认地址；
- 自动选择其他地址；

由 Design 决定。

---

## 九、安全要求

必须验证：

```text
Current Subject Type = MEMBER
```

涉及会员私有数据时还必须验证：

```text
Current Member
=
Resource Owner
```

即：

```text
认证
+
资源归属
```

两层检查。

---

## 十、验收标准

- 游客可以完成会员注册；
- 重复登录标识不能重复注册；
- 密码不以明文保存；
- MEMBER 可以正常登录；
- MEMBER Token 与 ADMIN Token 正确隔离；
- Access Token / Refresh Token 正常工作；
- 可以查看和修改本人会员资料；
- 可以新增、修改、删除收货地址；
- 可以设置默认地址；
- 一个会员默认地址规则正确；
- 用户 A 无法访问用户 B 的地址；
- 退出登录正常；
- mall-web 登录状态正确；
- 核心认证和资源归属测试通过。

---

## 十一、非本需求范围

本需求不负责：

- RBAC；
- 管理员；
- 商品；
- 购物车；
- 订单；
- 支付；
- 优惠券；
- 积分；
- 会员等级。

---

# REQ-M3-002 商城商品浏览体验

**阶段：** M3 商城基础  
**类型：** 商城商品体验需求  
**优先级：** P0  
**前置依赖：** REQ-M2-003、REQ-M2-004  
**主要服务：** mall-product、mall-inventory  
**主要前端：** mall-web

---

## 一、需求目标

基于 M2 已建立的真实商品和库存数据，实现商城用户侧商品浏览能力。

完成后，用户可以：

- 访问商城首页；
- 浏览分类；
- 查看商品列表；
- 查看商品详情；
- 选择 SKU；
- 查看价格；
- 查看必要库存状态；
- 为加入购物车做好准备。

M3 商品页面必须使用真实后端 Product / SKU 数据。

禁止使用静态 Mock 商品作为最终实现。

---

## 二、商城首页

建立商城基础首页。

M3 首页重点用于：

- 商城入口；
- 分类入口；
- 商品展示；
- 推荐区域基础结构。

可以包含：

- Banner；
- 分类入口；
- 新品；
- 推荐商品；
- 热门商品。

具体首页运营策略不要求复杂化。

M3 的目标是：

```text
真正能够进入商品浏览路径
```

而不是建设完整营销平台。

---

## 三、分类浏览

商城用户能够查看有效商品分类。

支持：

```text
分类
↓
商品列表
```

只展示商城可用的有效分类和商品。

后台禁用分类后的商城表现必须符合 M2 规则。

---

## 四、商品列表

建立商品列表页面。

至少支持：

- 分页；
- 分类筛选；
- 品牌筛选；
- 基础排序；
- 商品图片；
- 商品名称；
- 商品价格。

M3 使用 Product 服务数据库查询即可。

完整：

```text
关键词全文搜索
Elasticsearch
复杂聚合筛选
```

属于 M5。

---

## 五、商品详情

商品详情至少展示：

- 商品名称；
- 商品图片；
- 品牌；
- 分类；
- 商品介绍；
- SKU；
- SKU 属性；
- SKU 价格；
- 必要可售状态。

商品详情必须明确区分：

```text
Product
```

和：

```text
SKU
```

真正加入购物车的是具体：

```text
skuId
```

而不是仅：

```text
productId
```

---

## 六、SKU 选择

例如商品：

```text
手机
```

存在：

```text
黑色 + 256GB
黑色 + 512GB
白色 + 256GB
白色 + 512GB
```

用户选择规格后，需要正确解析到唯一 SKU。

SKU 变化时：

- 价格；
- 图片；
- 可售状态；

等信息应按照真实 SKU 数据变化。

---

## 七、库存展示

Product Context 不拥有真实库存。

因此商城需要库存状态时：

```text
mall-web
↓
Java API
↓
mall-inventory
```

获取库存信息。

可以对用户展示：

```text
有货
库存不足
缺货
```

不一定必须直接显示精确库存数字。

具体用户体验由 Design 决定。

---

## 八、库存展示不是交易保证

必须明确：

商品详情看到：

```text
有库存
```

不意味着稍后下单一定成功。

最终交易库存校验必须发生在：

```text
M4 创建订单 / Lock Inventory
```

因此：

```text
商品页库存
=
展示信息
```

而：

```text
订单库存锁定
=
交易约束
```

两者不能混淆。

---

## 九、游客访问

以下功能原则上允许游客使用：

- 首页；
- 分类；
- 商品列表；
- 商品详情。

用户无需登录即可浏览商品。

需要会员身份的动作，例如某些私人数据操作，再进入登录流程。

---

## 十、错误与空状态

商城前端需要处理：

- 商品不存在；
- 商品已下架；
- SKU 已失效；
- 商品暂无库存；
- 网络错误；
- 空分类；
- 空商品列表。

不能全部以 JavaScript 异常或空白页面结束。

---

## 十一、验收标准

- 游客可以访问商城；
- 首页可以展示真实商品数据；
- 分类可以正常浏览；
- 商品列表支持基础分页；
- 分类筛选正确；
- 品牌筛选正确；
- 商品详情数据正确；
- Product / SKU 正确区分；
- 选择规格能够定位正确 SKU；
- SKU 价格正确；
- SKU 库存状态来自 Inventory；
- 下架商品不能作为正常可售商品访问；
- 失效 SKU 不能正常加入后续交易；
- 页面具备基础 Loading / Empty / Error 状态；
- mall-web build / lint / type-check 通过。

---

## 十二、非本需求范围

本需求不负责：

- Elasticsearch 搜索；
- AI 推荐；
- 收藏；
- 评论；
- 营销；
- 优惠券；
- 下单；
- 支付。

---

# REQ-M3-003 购物车

**阶段：** M3 商城基础  
**类型：** 商城核心需求  
**优先级：** P0  
**前置依赖：** REQ-M2-003、REQ-M2-004、REQ-M3-001、REQ-M3-002  
**主要服务：** mall-cart  
**主要前端：** mall-web  
**主要基础设施：** Redis

---

## 一、需求目标

建立商城购物车能力，使用户能够将真实 SKU 加入购物车，并对购物车商品进行统一管理，为 M4 订单结算提供输入。

至少支持：

- 加入购物车；
- 查看购物车；
- 修改数量；
- 删除商品；
- 单选；
- 多选；
- 全选；
- 商品有效性校验；
- 最新价格展示；
- 库存状态展示；
- 登录前后购物车处理。

---

## 二、购物车存储

购物车建议使用：

```text
Redis
```

作为主要存储。

购物车属于：

```text
临时交易准备状态
```

不需要为了简单购物车状态建立复杂关系型数据库模型。

具体 Redis Key 和数据结构由 Design 阶段确定。

---

## 三、购物车条目

购物车的核心引用应是：

```text
memberId
+
skuId
```

并维护购物车自身状态，例如：

```text
quantity
selected
createdAt
updatedAt
```

但购物车不能将：

```text
商品名称
商品价格
商品状态
库存
```

永久视为自己的权威数据。

这些仍应来源于：

```text
mall-product
mall-inventory
```

---

## 四、加入购物车

用户选择具体 SKU 后，可以加入购物车。

加入前至少需要校验：

- Product 存在；
- Product 可售；
- SKU 存在；
- SKU 有效；
- 数量合法。

是否在加入购物车阶段强制要求库存充足，由 Design 确定。

但即使加入成功：

```text
也不代表库存已经锁定。
```

购物车不能提前锁库存。

---

## 五、相同 SKU 合并

同一个会员重复加入同一个 SKU 时，原则上：

```text
增加 quantity
```

而不是产生无限多个重复购物车条目。

例如：

第一次：

```text
SKU-A × 1
```

再次加入：

```text
SKU-A × 2
```

具体数量上限需要定义。

---

## 六、修改数量

支持修改购物车 SKU 数量。

必须校验：

```text
quantity > 0
```

并设置合理数量上限。

购物车数量不应导致：

- 负数；
- 0 条目长期存在；
- Integer Overflow 等异常。

---

## 七、删除购物车

支持：

- 删除单条；
- 批量删除；

只能操作当前 MEMBER 自己的购物车。

---

## 八、选择状态

支持：

- 单项选择；
- 取消选择；
- 全选；
- 取消全选。

选择状态用于后续：

```text
Checkout Preview
```

决定用户准备购买哪些 SKU。

---

## 九、购物车实时校验

这是购物车最重要的规则之一。

购物车中保存的是用户过去加入的 SKU。

但当前商品状态可能已经改变：

```text
加入时价格 = 100
现在价格 = 120

加入时有货
现在缺货

加入时上架
现在下架
```

因此查看购物车时需要根据 Product / Inventory 最新状态进行校验。

必须能够识别：

- 商品已下架；
- SKU 已失效；
- 价格变化；
- 库存不足；
- 商品不存在。

---

## 十、价格处理

购物车可以展示当前价格。

但：

```text
购物车价格
≠
订单最终成交价格
```

最终价格必须在：

```text
REQ-M4-001 订单预览与创建
```

重新计算和确认。

禁止直接信任浏览器传来的：

```text
price
totalAmount
```

创建订单。

---

## 十一、库存处理

购物车可以查询实时库存状态。

但是购物车：

```text
不锁库存
```

例如：

```text
用户把最后一件商品放购物车 3 天
```

不能导致其他用户 3 天都买不了。

正式 Lock Inventory 只能发生在：

```text
订单创建
```

阶段。

---

## 十二、游客购物车

M3 建议支持基础游客购物车能力。

游客未登录时，可以将购物车保存在：

```text
Browser Local Storage
```

或 Design 确定的前端临时存储。

游客：

```text
浏览商品
↓
加入购物车
↓
登录
```

登录成功后，应具备游客购物车与 MEMBER 购物车合并能力。

---

## 十三、购物车合并

游客登录后：

```text
Guest Cart
+
Member Cart
↓
Merged Member Cart
```

相同 SKU 应按照既定规则合并。

例如：

```text
Guest:
SKU-A × 2

Member:
SKU-A × 1
```

合并后：

```text
SKU-A × 3
```

同时仍需遵守最大购买数量等规则。

合并操作应具备合理幂等性，避免页面重试导致数量反复累加。

---

## 十四、购物车 API 安全

服务端 MEMBER 购物车必须从：

```text
SecurityContext
```

获取：

```text
memberId
```

而不是相信前端传：

```text
memberId=123
```

否则可能出现：

```text
修改 memberId
→ 操作别人的购物车
```

所有会员购物车操作必须验证资源归属。

---

## 十五、跨服务访问

mall-cart 需要：

```text
Product Query
Inventory Query
```

但不得：

```text
SELECT mall_product.xxx
SELECT mall_inventory.xxx
```

必须通过已经定义的内部 API / Contract 获取。

## 十七、购物车核心规则

必须保持：

```text
Cart
≠
Order
```

购物车只是：

```text
Purchase Intention
```

不是：

```text
Transaction Commitment
```

因此：

- 不锁库存；
- 不产生订单号；
- 不保存成交价；
- 不产生支付状态。

---

## 十八、验收标准

- 登录会员可以加入 SKU 到购物车；
- 同 SKU 重复加入正确合并；
- 可以修改商品数量；
- 可以删除购物车商品；
- 可以单选、多选、全选；
- 购物车只操作当前用户数据；
- 商品下架后购物车能够识别失效；
- SKU 失效后能够识别；
- 价格变化能够展示最新价格；
- 库存不足能够提示；
- 购物车不锁库存；
- 购物车价格不作为订单最终可信价格；
- Guest Cart 可以正常工作；
- 登录后 Guest Cart 可以合并到 Member Cart；
- 重复合并不会异常重复增加；
- mall-cart 不直接访问 Product / Inventory 数据库；
- 核心购物车测试通过；
- mall-web 购物车页面正常。

- 优惠券；
- 运费；

> 注意点：必须先调整

1. 统一把所有业务 ID 输出为字符串
   当前 Snowflake ID 超过 JavaScript 安全整数范围。实际商品 ID：
   2099488396675276801
   浏览器已经显示成：
   2099488396675276800
   如果继续使用数字，M3 购物车可能把商品或 SKU 传错。商品、SKU、会员、地址、购物车条目等 ID 都应采用 JSON 字符串，前端类型也使用 string。当前 DTO 仍然使用 long：[MallProductDtos.java](D:\Desktop\ai-platform\implementation\ai-platform-backend\mall-services\mall-product\src\main\java\com\ai\mall\product\interfaces\rest\mall\dto\MallProductDtos.java)。
2. 会员注册方式不能继续推迟
   [M3.md](D:\Desktop\ai-platform\docs\需求\M3\M3.md) 把用户名、手机号、邮箱、验证码的组合全部留到 Design，导致需求本身无法估算和验收。
   建议 M3 首期明确为：

- 用户名 + 密码注册
- 用户名 + 密码登录
- 手机号、邮箱作为资料字段
- 短信/邮件验证码登录放后续阶段
  否则还需要通知服务、验证码限流、防刷、有效期等额外能力。

3. 明确 Identity 与 Member 创建的一致性
   “注册失败不能产生不完整会员数据”跨越 mall-identity 和 mall-member 两个数据库，不能靠普通事务保证。
   需求里应明确：

- Identity 创建成功后通过事件初始化 Member Profile；
- Profile 初始化操作幂等；
- 失败可以重试；
- 注册完成状态在 Profile 初始化成功后才对外可用，或者接受短暂最终一致；
- 不允许跨库事务或跨服务直接写表。

4. 补齐商城公开 API
   M3 提到分类和库存展示，但当前只有：

- 公开商品列表、详情；
- 后台分类接口；
- 后台库存接口；
- 内部库存/商品接口。
  因此 M3 应明确新增：
- GET /api/mall/categories/tree
- GET /api/mall/brands
- 商品列表排序参数
- 批量 SKU 可售状态查询
- 商品详情所需的库存聚合方式
  不能让浏览器访问 /api/internal/\*\*，也不能在商品列表逐个查询库存造成 N+1。

5. 商品价格接口目前不满足 M3
   当前商品列表的 minPrice、maxPrice 固定返回 null：[MallProductController.java](D:\Desktop\ai-platform\implementation\ai-platform-backend\mall-services\mall-product\src\main\java\com\ai\mall\product\interfaces\rest\mall\MallProductController.java)。
   M3 必须要求：

- 列表返回启用 SKU 的最低价和最高价；
- 无有效 SKU 的商品不得出现在商城；
- 详情选择 SKU 后展示该 SKU 的真实价格；
- 金额统一使用分，禁止浮点数。

6. 游客购物车存在前后矛盾
   文档说“建议支持”游客购物车：[M3.md](D:\Desktop\ai-platform\docs\需求\M3\M3.md)，但验收标准和 DoD 又把它列为必做：[M3.md](D:\Desktop\ai-platform\docs\需求\M3\M3.md)。

7. Redis 购物车需要补充可靠性规则
