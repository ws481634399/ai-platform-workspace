可以。M4 是整个项目第一个真正形成**交易闭环**的阶段，建议保持 **4 个 SDD 级 Requirement**：

M4 的目标是先把同步交易链路完整跑通；RocketMQ、Outbox、延迟消息、最终一致性等放到 M7 再增强。

# REQ-M4-001 订单预览与创建

**阶段：** M4 订单交易闭环  
**类型：** 核心交易需求  
**优先级：** P0  
**前置依赖：** REQ-M2-003、REQ-M2-004、REQ-M3-001、REQ-M3-003  
**主要服务：** mall-order  
**协作服务：** mall-product、mall-inventory、mall-member  
**主要前端：** mall-web

---

## 一、需求目标

建立订单预览和订单创建能力。

用户从：

- 购物车；
- 商品详情立即购买；

进入订单确认页时，需要重新读取真实业务数据，而不是直接信任前端或购物车缓存。

订单创建成功后必须形成：

```text
真实订单
+
订单项
+
商品快照
+
地址快照
+
金额快照
+
库存锁定
```

订单进入：

```text
待支付
```

状态。

---

## 二、订单预览

建立 Checkout Preview。

订单预览不是正式订单，不产生正式订单号，也不锁定库存。

订单预览至少需要：

- 当前会员；
- 待购买 SKU；
- 购买数量；
- 当前商品信息；
- 当前 SKU 信息；
- 当前销售价格；
- 当前库存状态；
- 当前收货地址；
- 商品金额；
- 应付金额。

数据必须以服务端重新查询结果为准。

---

## 三、禁止信任前端价格

前端可以提交：

```text
skuId
quantity
addressId
```

等必要业务参数。

但是不得信任前端提交：

```text
productName
skuName
price
totalAmount
discountAmount
payAmount
```

直接创建订单。

必须：

```text
Client
↓
skuId + quantity
↓
Order Service
↓
Product Service
↓
重新获取真实商品与价格
↓
服务端计算金额
```

防止通过修改浏览器参数：

```text
price = 0.01
```

低价下单。

---

## 四、商品实时校验

订单预览和正式创建时必须重新校验：

- Product 是否存在；
- Product 是否上架；
- SKU 是否存在；
- SKU 是否有效；
- 当前价格；
- 必要销售状态。

即使商品：

```text
已经在购物车
```

也不代表当前一定还能购买。

---

## 五、库存实时校验

预览阶段可以查询当前库存。

但：

```text
Preview
```

不锁库存。

正式创建订单时：

```text
必须 Lock Inventory
```

库存不足：

```text
订单创建失败
```

不得先创建一个有效待支付订单，再发现没有库存。

---

## 六、地址校验

订单使用：

```text
addressId
```

时必须验证：

```text
Address.memberId
=
CurrentMember.memberId
```

会员不能使用其他会员的地址。

同时需要复制当前收货地址形成：

```text
Address Snapshot
```

订单创建后，即使用户修改个人地址：

历史订单地址也不能变化。

---

## 七、订单商品快照

创建订单时必须保存商品快照。

至少考虑：

```text
productId
skuId
productName
skuName
skuAttributes
image
unitPrice
quantity
subtotal
```

具体字段由 Design 确定。

这样商品后续：

- 改名；
- 修改图片；
- 修改价格；
- 下架；

都不会改变历史订单内容。

---

## 八、金额计算

至少建立：

```text
商品总金额
应付金额
```

首期没有优惠券时，可以：

```text
payAmount = goodsAmount
```

但金额模型应为未来：

- 优惠；
- 运费；
- 营销；

预留合理扩展边界。

金额计算必须：

- 使用精确 Decimal / BigDecimal；
- 禁止 float / double；
- 服务端计算；
- 满足金额不变量。

---

## 九、订单模型

订单至少需要表达：

```text
Order
OrderItem
```

以及：

```text
orderNo
memberId
status
goodsAmount
payAmount
receiverSnapshot
createdAt
```

等必要交易信息。

具体领域模型由 Design 阶段完成。

---

## 十、订单号

订单需要生成全局唯一：

```text
orderNo
```

要求：

- 唯一；
- 不依赖数据库自增 ID 暴露内部实现；
- 能作为业务查询和跨服务 Reference；
- 高并发下不重复。

具体生成策略由 Design 决定。

---

## 十一、订单状态

M4 应建立明确订单状态机。

至少能够表达类似：

```text
PENDING_PAYMENT
PAID
SHIPPED
COMPLETED
CANCELLED
```

具体命名由 Design 最终统一。

禁止在不同服务中同时出现：

```text
WAIT_PAY
PENDING
PAYING
UNPAID
```

等互不一致状态。

---

## 十二、创建订单与库存锁定

核心逻辑：

```text
创建订单请求
↓
校验 MEMBER
↓
校验地址
↓
获取 Product / SKU
↓
重新获取价格
↓
计算金额
↓
请求 Inventory Lock
↓
创建订单
↓
保存订单快照
↓
返回订单
```

需要重点处理：

```text
库存锁定成功
但是订单保存失败
```

场景。

不能让库存永久悬挂。

具体补偿由本 Requirement 与 `REQ-M4-004` 共同设计。

---

## 十三、订单创建幂等

提交订单必须考虑：

```text
用户双击
网络重试
浏览器重复提交
Gateway 重试
```

不能产生多个完全相同订单并重复锁库存。

需要设计：

```text
Submit Token
Idempotency Key
Business Key
```

等适合当前项目的幂等方案。

---

## 十四、购物车处理

订单创建成功后，可以根据业务规则清理：

```text
已成功购买的购物车选中项
```

但必须保证：

订单创建失败
≠
购物车被错误清空。

---

## 十五、验收标准

- 可以从购物车进入订单预览；
- 可以从立即购买进入订单预览；
- Preview 不创建订单；
- Preview 不锁库存；
- 服务端重新获取商品和价格；
- 前端篡改价格无法低价下单；
- 地址必须属于当前会员；
- 地址形成快照；
- 商品形成快照；
- 金额由服务端计算；
- 库存足够时可以创建订单；
- 库存不足时创建失败；
- 创建成功后库存正确锁定；
- 重复提交不会产生重复有效订单和重复锁库存；
- 订单号唯一；
- 购物车只在创建成功后按规则处理；
- 订单创建核心测试通过。

---

## 十六、非本需求范围

本需求不负责：

- 真正支付网关；
- RocketMQ；
- Outbox；
- 自动超时取消；
- 发货；
- 收货；
- 退款。

---

# REQ-M4-002 模拟支付与订单取消

**阶段：** M4 订单交易闭环  
**类型：** 交易状态需求  
**优先级：** P0  
**前置依赖：** REQ-M4-001  
**主要服务：** mall-order、mall-inventory  
**主要前端：** mall-web

---

## 一、需求目标

建立订单待支付后的：

```text
模拟支付
+
主动取消
```

能力。

完成后订单能够从：

```text
PENDING_PAYMENT
```

进入：

```text
PAID
```

或者：

```text
CANCELLED
```

并正确驱动库存状态变化。

---

# 二、模拟支付

本项目首期不接入真实第三方支付。

建立：

```text
Mock Payment
```

用于完整验证交易状态机。

商城用户在待支付订单中可以执行：

```text
模拟支付成功
```

模拟支付必须仍然按照真实支付系统需要的安全和幂等思想设计。

不能简单：

```text
UPDATE order SET status='PAID'
```

结束。

---

## 三、支付核心规则

支付前必须验证：

```text
当前用户
=
订单所有者
```

以及：

```text
订单状态
=
PENDING_PAYMENT
```

不能：

```text
已取消订单
→ 再支付成功
```

不能：

```text
其他用户订单
→ 被当前用户支付
```

---

## 四、支付幂等

支付属于典型重复通知场景。

即使 M4 使用模拟支付，也必须设计：

```text
相同支付成功请求多次到达
```

只能产生一次有效状态迁移。

例如：

```text
PENDING_PAYMENT
↓
PAID
```

第二次重复支付：

```text
PAID
↓
保持 PAID
```

不得再次扣库存。

---

## 五、支付后库存确认扣减

M4 当前同步流程：

```text
支付成功
↓
Inventory Confirm Deduction
↓
Locked → Deducted
```

要求：

- 对应订单必须存在有效锁定；
- 确认扣减幂等；
- 重复支付不能重复扣减。

M7 会再将这条链路升级为可靠消息驱动。

---

# 六、会员主动取消订单

会员可以取消满足条件的订单。

通常：

```text
PENDING_PAYMENT
```

允许取消。

已经：

```text
PAID
SHIPPED
COMPLETED
```

不能直接通过普通“取消订单”动作处理。

支付后的售后属于后续退款 / 售后体系。

---

## 七、取消后库存释放

核心流程：

```text
PENDING_PAYMENT
↓
Cancel
↓
Inventory Release
↓
Order CANCELLED
```

需要保证：

- 已锁定库存释放；
- 释放幂等；
- 重复取消不重复增加库存。

---

# 八、支付和取消并发

必须考虑：

```text
支付
```

和：

```text
取消
```

几乎同时发生。

例如：

```text
线程 A：PAY
线程 B：CANCEL
```

最终只能有一个合法状态迁移生效。

不能出现：

```text
订单 = PAID
但是库存已经 Release
```

或者：

```text
订单 = CANCELLED
但是库存已经 Deduct
```

需要通过：

- 状态条件更新；
- 乐观锁；
- Domain State Machine；

等方式保证并发一致性。

具体策略由 Design 决定。

---

# 九、订单状态历史

关键状态变化需要形成：

```text
OrderStatusHistory
```

至少记录：

```text
orderId/orderNo
fromStatus
toStatus
operation
operator
occurredAt
reason
```

便于：

- 审计；
- 排错；
- 展示订单轨迹；
- 后续补偿。

---

# 十、mall-web 支付取消体验

订单详情 / 待支付页面至少支持：

```text
立即支付
取消订单
```

但必须根据状态决定允许的操作。

例如：

```text
PENDING_PAYMENT
→ 支付 / 取消

PAID
→ 不再显示支付

CANCELLED
→ 不再显示支付
```

前端状态控制只是体验。

真正状态校验必须在后端完成。

---

## 十一、验收标准

- 待支付订单可以模拟支付；
- 非本人订单不能支付；
- 已取消订单不能正常支付；
- 支付成功订单状态正确；
- 支付成功后库存确认扣减正确；
- 重复支付不会重复扣库存；
- 待支付订单可以主动取消；
- 非本人订单不能取消；
- 取消后库存正确释放；
- 重复取消不会重复释放；
- 支付和取消竞争后只能产生一个合法最终结果；
- 所有关键状态迁移存在历史记录；
- 前端操作与订单状态匹配；
- 支付/取消领域测试通过。

---

## 十二、非本需求范围

本需求不负责：

- 微信支付；
- 支付宝；
- 银行支付；
- 正式支付回调安全；
- 退款；
- 自动超时关闭；
- MQ 支付事件。

---

# REQ-M4-003 订单查询与履约

**阶段：** M4 订单交易闭环  
**类型：** 订单履约需求  
**优先级：** P0  
**前置依赖：** REQ-M4-001、REQ-M4-002  
**主要服务：** mall-order  
**主要前端：** mall-web、mall-admin

---

## 一、需求目标

建立用户侧订单查询和后台订单履约能力，使已经支付的订单可以继续完成：

```text
查询
↓
后台发货
↓
会员确认收货
↓
订单完成
```

形成完整订单生命周期。

---

# 二、会员订单列表

mall-web 提供：

```text
我的订单
```

至少支持：

- 全部；
- 待支付；
- 待发货；
- 待收货；
- 已完成；
- 已取消；

等基础状态筛选。

具体 UI 状态文案可以与领域状态做映射。

---

# 三、会员订单详情

会员可以查看本人订单详情。

至少展示：

- orderNo；
- 订单状态；
- 商品快照；
- SKU 快照；
- 成交价；
- 数量；
- 金额；
- 收货地址快照；
- 创建时间；
- 支付时间；
- 发货时间；
- 完成时间；
- 状态历史等必要信息。

---

# 四、订单资源归属

这是重要安全规则。

所有会员订单接口必须：

```text
CurrentMember.memberId
=
Order.memberId
```

禁止：

```text
GET /orders/{otherOrderId}
```

通过猜测订单 ID 查询别人的订单。

即使：

```text
订单 ID / orderNo
```

正确，也必须进行资源归属校验。

---

# 五、后台订单查询

mall-admin 提供运营管理订单能力。

至少支持：

- 订单列表；
- orderNo 查询；
- 会员查询条件；
- 状态筛选；
- 时间范围；
- 订单详情。

接口必须受到 M1 RBAC 控制。

---

# 六、后台发货

管理员可以对符合条件的订单执行：

```text
Ship
```

通常只有：

```text
PAID
```

订单允许发货。

需要保存必要物流基础信息，例如：

```text
deliveryCompany
trackingNo
shippedAt
```

具体首期物流模型由 Design 确定。

本项目不需要接入真实物流平台即可完成核心闭环。

---

# 七、发货幂等和状态限制

不能：

```text
PENDING_PAYMENT
→ SHIPPED
```

不能：

```text
CANCELLED
→ SHIPPED
```

重复发货请求需要按照领域规则处理。

所有状态迁移必须通过领域行为完成，而不是 Controller 任意修改 status。

---

# 八、确认收货

会员收到商品后可以：

```text
Confirm Receipt
```

通常：

```text
SHIPPED
↓
COMPLETED
```

只能：

```text
订单本人
```

确认收货。

未发货订单不能确认收货。

---

# 九、订单状态机

M4 最终需要形成完整状态机，例如：

```text
                    ┌──── Cancel ───→ CANCELLED
                    │
PENDING_PAYMENT ────┤
                    │
                    └──── Pay
                           ↓
                          PAID
                           ↓
                          Ship
                           ↓
                        SHIPPED
                           ↓
                    Confirm Receipt
                           ↓
                       COMPLETED
```

允许的状态迁移必须集中管理。

禁止在不同：

```text
Controller
Service
Mapper
```

中随意：

```java
order.setStatus(...)
```

改变订单状态。

---

# 十、订单操作权限

两类身份权限不同：

```text
MEMBER
```

可以：

- 查看本人订单；
- 支付本人订单；
- 取消本人符合条件订单；
- 确认本人订单收货。

```text
ADMIN
```

根据 RBAC 可以：

- 查询后台订单；
- 查看详情；
- 发货。

不能因为 ADMIN 可以后台操作，就直接绕过所有领域状态规则。

---

# 十一、验收标准

- MEMBER 可以查看自己的订单列表；
- 支持基础状态筛选；
- MEMBER 可以查看自己的订单详情；
- MEMBER 无法读取其他用户订单；
- ADMIN 可以按照权限查看订单；
- PAID 订单可以发货；
- 未支付订单不能发货；
- 已取消订单不能发货；
- 发货信息可以保存；
- SHIPPED 订单可以由本人确认收货；
- 未发货订单不能确认收货；
- 非订单所有者不能确认收货；
- 完成后订单状态为 COMPLETED；
- 所有状态变化形成历史记录；
- 状态机不允许非法跳转；
- mall-web / mall-admin 页面正常；
- 权限测试通过。

---

# 十二、非本需求范围

本需求不负责：

- 真实物流查询；
- 自动确认收货；
- 售后退款；
- 评价；
- 发票；
- MQ 履约事件。

---

# REQ-M4-004 交易异常与补偿基础

**阶段：** M4 订单交易闭环  
**类型：** 交易可靠性需求  
**优先级：** P0  
**前置依赖：** REQ-M4-001、REQ-M4-002  
**主要服务：** mall-order、mall-inventory

---

## 一、需求目标

处理订单同步交易链路中可能出现的部分失败，避免出现明显业务脏状态。

M4 不建设完整分布式事务平台，但必须解决核心同步交易中的基本异常恢复问题。

需要重点处理：

```text
库存锁定成功
订单创建失败
```

```text
订单取消成功
库存释放失败
```

```text
支付状态变更
库存确认扣减失败
```

等情况。

---

# 二、为什么 M4 必须有补偿

微服务之间不存在一个简单：

```text
@Transactional
```

可以覆盖：

```text
mall-order
+
mall-inventory
```

两个数据库。

因此可能出现：

```text
Inventory COMMIT
↓
Order FAIL
```

如果不处理：

库存被锁

- 没有订单

形成库存泄漏。

---

# 三、订单创建失败补偿

重点场景：

```text
Inventory Lock SUCCESS
↓
Order Persist FAIL
```

必须：

```text
触发 Inventory Release
```

释放对应库存。

释放必须使用稳定 Business Reference，例如：

```text
orderNo
reservationId
```

等，由 Design 确定。

---

# 四、补偿失败记录

如果：

```text
释放库存
```

本身又失败：

不能：

```text
catch(Exception e) {
    log.error(...);
}
```

然后永久丢弃。

必须形成可追踪失败记录。

例如：

```text
CompensationTask
FailureTask
```

记录：

- businessType；
- businessId；
- operation；
- status；
- retryCount；
- lastError；
- nextRetryAt；
- createdAt。

具体模型由 Design 确定。

---

# 五、基础重试

M4 可以建立简单：

```text
Retry
```

能力。

用于：

```text
临时网络失败
服务短暂不可用
```

但重试必须：

- 有最大次数；
- 有间隔；
- 具有幂等性；
- 不进行无限循环；
- 不因为重试导致重复业务操作。

---

# 六、库存操作必须幂等

以下操作必须支持重复请求：

```text
Lock
Release
Confirm
```

例如：

```text
Order 1001 Release
↓
成功
↓
网络超时
↓
Order 不知道成功
↓
再次 Release
```

Inventory 必须返回正确幂等结果。

不能再次增加库存。

---

# 七、状态迁移幂等

同样：

```text
Pay
Cancel
Ship
Confirm Receipt
```

等重要动作必须按照当前状态决定：

- 首次执行；
- 重复执行；
- 非法执行。

不得通过重复请求造成多次副作用。

---

# 八、关键操作审计

需要能够追踪：

```text
谁
在什么时候
对哪个订单
执行了什么操作
从什么状态
变成什么状态
结果如何
```

至少通过：

```text
OrderStatusHistory
+
日志 / TraceId
```

实现基础追踪。

---

# 九、失败可观测性

关键交易异常必须有明确日志。

例如：

```text
orderNo
operation
traceId
error
```

但不能记录：

- Password；
- Token；
- Secret；
- 不必要的完整个人敏感信息。

---

# 十、补偿人工处理基础

对于超过自动重试次数仍然失败的任务，需要能够：

```text
被查询
```

并为后续：

```text
人工重试
```

预留能力。

M4 可以只提供后台或内部基础能力，不需要建设复杂运维平台。

---

# 十一、M4 与 M7 的边界

M4 负责：

```text
同步调用
+
幂等
+
基本补偿
+
失败记录
+
简单重试
```

M7 再升级为：

```text
RocketMQ
+
Outbox
+
可靠事件发布
+
Consumer Idempotency
+
Delay Message
+
Dead Letter
+
最终一致性
```

因此 M4 不需要为了可靠性直接提前实现完整 MQ 架构。

---

# 十二、验收标准

至少模拟：

### 场景 A

```text
库存 Lock 成功
↓
订单保存失败
```

最终：

```text
库存得到释放
```

或者形成：

```text
明确可恢复 Compensation Task
```

---

### 场景 B

```text
取消订单
↓
库存 Release 首次失败
```

可以进入重试或失败任务机制。

---

### 场景 C

```text
支付成功处理重复执行
```

不得重复扣减库存。

---

### 场景 D

```text
取消请求重复执行
```

不得重复释放库存。

---

### 场景 E

关键失败能够通过：

```text
orderNo + traceId
```

定位。

---

## 十三、非本需求范围

本需求不负责：

- RocketMQ；
- Outbox；
- Delay Message；
- Dead Letter Queue；
- Seata；
- 分布式强事务；
- 完整监控告警平台。

---

# M4 Integration Gate

四个 Requirement 完成以后，需要执行完整交易联调。

---

## 场景一：完整成功交易

```text
MEMBER 登录
↓
商品详情
↓
SKU 有库存
↓
加入购物车
↓
订单预览
↓
选择收货地址
↓
提交订单
↓
服务端重新校验价格
↓
锁库存
↓
生成 PENDING_PAYMENT
↓
模拟支付
↓
确认扣减库存
↓
订单 PAID
↓
ADMIN 后台发货
↓
订单 SHIPPED
↓
MEMBER 确认收货
↓
COMPLETED
```

整个流程必须成功。

---

# 场景二：库存不足

准备：

```text
Available = 1
```

提交：

```text
quantity = 2
```

结果必须：

```text
创建失败
库存不为负
不存在有效待支付订单
```

---

# 场景三：价格变化

```text
加入购物车时
Price = 100
↓
后台修改价格
Price = 120
↓
订单预览
```

必须使用：

```text
120
```

作为当前价格。

不能信任购物车旧价格。

---

# 场景四：前端篡改价格

客户端提交：

```text
price = 0.01
```

后端仍然按照 Product 当前真实价格计算。

---

# 场景五：重复提交订单

```text
同一个 Submit Request
× 2
```

不能产生：

```text
2 个订单
+
2 次库存锁定
```

---

# 场景六：支付重复

```text
Pay Success
× 2
```

最终：

```text
Order = PAID
Inventory = 只扣一次
```

---

# 场景七：取消重复

```text
Cancel
× 2
```

最终：

```text
Order = CANCELLED
Inventory = 只释放一次
```

---

# 场景八：支付取消竞争

同时：

```text
Pay
||
Cancel
```

最终只能：

```text
PAID
```

或：

```text
CANCELLED
```

其中一个合法状态。

库存最终状态必须与订单状态一致。

---

# 场景九：订单越权

```text
Member A
```

尝试查看：

```text
Member B Order
```

必须拒绝。

---

# 场景十：库存锁定后的订单失败

模拟：

```text
Inventory Lock PASS
Order Persist FAIL
```

验证：

```text
Inventory Release
```

或补偿任务正确形成。

# M4 完成后的系统状态

系统正式拥有第一条完整交易链路：

```text
mall-web
│
├── Cart
│
├── Checkout
│
├── Order
│
├── Mock Pay
│
└── Confirm Receipt
│
▼
mall-order
│
├── Order
├── OrderItem
├── Snapshot
├── Amount
├── State Machine
├── Idempotency
└── Compensation
│
├─────────────→ mall-product
│               商品 / SKU / Price
│
├─────────────→ mall-inventory
│               Lock
│               Release
│               Confirm
│
└─────────────→ mall-member
                Address
```

后台：

```text
mall-admin
↓
Order Management
↓
Ship
↓
mall-order
```

完整订单生命周期：

```text
PENDING_PAYMENT
       │
       ├──── Cancel ───→ CANCELLED
       │
       └──── Pay
              ↓
             PAID
              ↓
             SHIP
              ↓
           SHIPPED
              ↓
       CONFIRM_RECEIPT
              ↓
          COMPLETED
```

M4 最终解决的是：

> **“用户真正买下商品之后，订单、价格、库存和履约如何保持业务一致，并最终完成一笔交易。”**

到这里，你这个项目已经不再只是“后台 CRUD + 商城页面”，而是真正具备了电商核心交易闭环。
