# REQ-M0-004 本地基础设施环境

**阶段：** M0 项目初始化  
**类型：** 工程基础需求  
**优先级：** P0  
**前置依赖：** 无强依赖，可与 `REQ-M0-001`、`REQ-M0-002`、`REQ-M0-003` 并行开发  
**实现范围：** Docker Compose、本地基础设施、环境配置、运行脚本与基础联调能力

---

## 一、需求目标

建立 AI 智能电商微服务平台统一的本地基础设施运行环境，为 Java 后端、前端和 AI Service 提供可重复启动、停止、验证和恢复的本地开发环境。

M0 阶段需要优先建立：

- MySQL；
- Redis；
- Nacos；
- MinIO；

所有基础设施统一通过 Docker Compose 管理。

完成本需求后，开发人员不需要在 Windows 本机分别安装 MySQL、Redis、Nacos、MinIO 等中间件，只需要 Docker 即可启动项目 M0 阶段所需基础设施。

本 Requirement 的核心目标是：

统一运行方式
+
统一网络
+
统一环境变量
+
统一数据持久化
+
统一健康检查
+
统一启动/停止方式
+
为 M0 联调提供基础环境

---

## 二、基础原则

本地基础设施统一使用：

```text
Docker
+
Docker Compose
````

开发机器本地只负责安装：

```text
Docker Desktop / Docker Engine
```

MySQL、Redis、Nacos、MinIO 等基础设施不得要求开发人员另外以 Windows Service 等方式安装。

原则：

```text
开发工具
→ 本地安装

基础设施
→ Docker 运行
```

暂不建立：

建议建立独立基础设施目录，例如：

```text
deploy/
├── docker-compose.infra.yml
├── .env.example
├── .gitignore
│
├── mysql/
│   └── init/
│
├── redis/
│
├── nacos/
│
├── minio/
│
└── scripts/
    ├── start.*
    ├── stop.*
    ├── status.*
    └── health.*
```

具体文件划分可由 Design 阶段调整。

如果项目已经存在部署目录，应优先复用现有结构，不得无理由重新创建另一套部署体系。

# 五、Docker Compose

建立统一：

```text
docker-compose.infra.yml
```

用于管理 M0 基础设施。

必须能够通过统一命令启动：

```bash
docker compose -f docker-compose.infra.yml up -d
```

停止：

```bash
docker compose -f docker-compose.infra.yml down
```

查看：

```bash
docker compose -f docker-compose.infra.yml ps
```

不应要求开发人员逐个执行：

```text
docker run mysql ...
docker run redis ...
docker run nacos ...
```

---

# 六、Docker Network

所有基础设施应加入统一 Docker Network。

例如语义上：

```text
ai-platform-network
```

使容器之间能够使用服务名称互相访问。

例如：

```text
mysql:3306
redis:6379
nacos:8848
minio:9000
```

容器内部不得依赖固定宿主机 IP。

# 七、MySQL

建立 MySQL 本地开发实例。

用于后续：

* identity；
* member；
* product；
* order；
* inventory；
* system；

等 Java 微服务的数据持久化。

## 要求

至少配置：

* MySQL 容器；
* Root Password；
* Character Set；
* Timezone；
* Volume；
* Health Check；
* 必要初始化能力。

统一字符集建议：

```text
utf8mb4
```

数据库配置必须通过环境变量注入。

禁止在 Compose 文件中提交真实生产密码。

---

## 数据库初始化

M0 可以创建项目运行所需的基础数据库。

例如根据后续微服务数据库规划建立对应 Schema。

但是：

> M0-004 只负责创建数据库环境，不负责创建商品、订单、库存等正式业务表。

正式业务表结构由各服务通过：

```text
Flyway Migration
```

管理。

不要在 Docker MySQL 初始化脚本中维护整个业务数据库 DDL。

正确职责：

```text
Docker
→ 创建 MySQL 与必要 Database

Flyway
→ 管理业务表版本
```

* 购物车；

* 权限缓存；
* 商品缓存；
* 分布式锁；

等具体业务逻辑。

# 十一、数据持久化

以下基础设施需要根据实际情况配置 Docker Volume：

```text
MySQL
Redis
Nacos
MinIO
```

重点保证：

```text
docker compose down
```

后重新：

```text
docker compose up -d
```

时，不会因为普通容器重建导致全部开发数据无条件丢失。

需要明确区分：

```text
Container
≠
Data
```

容器可以重建，开发数据通过 Volume 保留。

# 十七、基础设施与应用配置边界

Docker 基础设施负责：

```text
服务运行
端口
Network
Volume
基础账号
Health Check
```

Java / AI 应用负责：

```text
如何连接这些基础设施
```

例如：

```text
MySQL Container
```

不应该知道：

```text
mall-order 如何配置 DataSource
```

同样：

```text
Nacos Container
```

不负责：

```text
mall-product 的 Spring Cloud 配置
```

避免部署配置和应用配置互相污染。

```text
LLM API Key
```


并通过：

```text
.env
```

管理。

`.env.example` 中只能提供：

```text
变量名

示例值/占位符
```

# 二十一、与 AI Service 的关系

M0 AI Service 不强制依赖：

```text
MySQL
Redis
MinIO
```

才能启动。

尤其 AI Service：

> 不允许通过本需求获得 Java 业务数据库直接连接能力。

AI Service 后续获取业务数据仍然通过 Java API。

MinIO 后续可以提供：

```text

```

但不在 M0 实现知识库业务。

---

# 二十二、禁止跨服务数据库访问

本地存在一个 MySQL 实例不意味着所有服务可以随意查询所有表。

必须继续遵守：

```text
Service
→ Own Database / Schema
```

边界。

禁止：

```text
mall-order
→ SELECT mall_product.xxx
```

禁止：

```text
AI Service
→ SELECT mall_order.xxx
```

Docker 只是提供运行基础设施，不改变微服务数据所有权。
